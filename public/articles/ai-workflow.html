PORTFOLIO · ENGINEERING PRACTICE

AI와 함께 일관된 시스템을 유지하기
workflow를 설계하고 운영한 사례

이 프로젝트의 핵심 작업물 — 9 개 Template, 6 개 ADR, 20 여 개 PR — 은 거의 모두 AI 도구와의 협업으로 만들어졌다. 다만 "AI가 코드를 생성했다" 라는 관점만으로는 이 프로젝트를 설명할 수 없다. 여기서 더 중요했던 일은 AI 제안의 reasoning 을 해석하고, trade-off 를 판단하며, 도메인 언어와 아키텍처를 일관되게 유지하는 workflow 를 설계하고 운영한 것 이다. 이 글은 그 workflow 의 구성과 운영 경험을 정리한다.

TL;DR · 한눈에

30초 요약

⚠ 문제
AI 가 매번 그럴듯한 코드를 내놓아도, 장기적으로 일관된 시스템을 유지하는 것은 별개의 문제. AI 는 영어 동의어에 흔들리고, 같은 결정을 다음 세션에서는 잊으며, non-deterministic 한 출력은 매번 새로 검토해야 한다.
🛠 해결
아이디어 → grill → CONTEXT/ADR → /to-issues → branch → TDD → PR 6-단계 루프 + AI 출력을 가두는 4 계층 deterministic guard (Zod / per-stage approval / validate rules / ESLint custom rule). AI 는 propose, 사람은 judge.
✓ 결과
Template 간 코드 0 공유 (β 모델), 인라인 색 리터럴 0 (ESLint error), Generate 파이프라인이 만든 Preset 도 같은 validate 게이트를 통과 — 한 사람 + AI 운영체제로 9 개 Template / 6 개 ADR / 12 개 SQL migration 을 일관되게 유지.
STEP 1 · 워크플로우 한 장

6-단계 루프 — 모든 작업이 통과하는 길

새로운 변경 사항은 항상 이 순서를 통과한다. 단계를 건너뛰면 도메인 언어가 흐트러지거나 다음 세션의 AI 가 같은 trade-off 를 다시 잊는다.

STEP 1
IDEA
"이 기능이 필요할 것 같다" — 사용자, AI, 또는 내가 떠올린 거친 아이디어
STEP 2
GRILL
/grill-with-docs — 기존 ADR / CONTEXT 와 충돌하는지, 더 단순한 길은 없는지 반복 질문
STEP 3
DOCS
결정이 굳으면 CONTEXT.md 용어 추가 / 정정, 중요한 trade-off 는 ADR 신규 생성
STEP 4
/to-issues
스코프를 tracer-bullet vertical slice 로 쪼개 GitHub Issue 생성 (ready-for-agent)
STEP 5
BUILD
Feature branch + TDD (Vitest, domain layer in-memory fake) + validate / lint 통과
STEP 6
REVIEW
PR 본문에 ADR 링크 + acceptance check, 사람이 reasoning 검증 후 merge
핵심 규칙 · STEP 2 (grill) 와 STEP 3 (docs) 는 비용처럼 보이지만 사실은 절약이다. 여기서 한 번 합의된 결정이 다음 세션의 AI 에게도 그대로 전달되기에, 같은 trade-off 를 두 번 토론하지 않는다. ADR 6 개는 모두 이 단계에서 만들어졌고, 이후 PR 본문에서 반복적으로 인용된다.
STEP 2 · grill-with-docs

AI 가 코드를 짜기 전에, 아이디어를 부순다

/grill-with-docs 는 AI 에게 답을 부탁하는 게 아니라 AI 가 나를 grill 하게 하는 도구다. 내 plan 을 기존 도메인 언어와 ADR 에 비추어 검증하고, 어떤 결정 분기가 미해결인지 끝까지 묻는다.

EXAMPLE · "Template 간 컴포넌트를 공유하면 안 되나?" → ADR-0001 도출

처음에 나는 "Hero 컴포넌트가 9 개 Template 디렉터리에 똑같이 복제되는 게 비효율적" 이라고 생각했다. DRY 가 본능이었다. 그래서 AI 에게 "이걸 src/sections/ 공용 풀로 추출하면 안 되나?" 라고 물었다.

처음 질문 — "왜 9 개 Template 가 다 자기 컴포넌트를 따로 들고 있어? src/sections/Hero.tsx 하나만 두고 import 하면 되지 않나?"

"디자인마다 레이아웃 구조, 컴포넌트 계층, 시각적 방향성이 크게 달라질 수 있어요. 공통 추상화를 강제하면 새 Template 가 들어올 때 추상화가 깨지거나 prop 폭발이 발생합니다. β 모델은 DRY 보다 isolation 을 우선 합니다 — 의도된 중복이에요."

"그럼 같은 카테고리 (cafe-default, cafe-cozy, cafe-modern) 안에서는?"

"같은 카테고리 안이라도 마찬가지입니다. 카테고리는 카탈로그 분류 버킷일 뿐 코드 공유 단위가 아닙니다. 미래에 multi-page 가 본격 확장되면 디렉터리가 library/ 에서 pages/<page>/sections/ 로 옮겨갈 가능성도 있는데, 그 때 cross-Template 공유 상태였다면 무너집니다."

이 대화 끝에 ADR-0001 (β 모델 — Template 단위 isolation 우선) 가 만들어졌다. 한 줄 핵심: "Hero 컴포넌트가 9 곳에 복제돼 있는데 추출해야 하지 않나" 라는 미래 PR 제안은 이 ADR 을 근거로 거절한다 — 의도된 중복이다. 이후 같은 제안이 다음 세션에서 다시 나와도 ADR 한 줄로 답을 끝낼 수 있다.

EXAMPLE · "Rich Design Tokens, 9 개 Template 다 한 번에 바꿔야 하지 않나?" → ADR-0005 도출

Issue #9 에서 풍부한 designTokens 패턴을 도입할 때, 나는 자연스럽게 "9 개 Template 다 한 번에 마이그하자" 고 제안했다.

"가능은 하지만 한 PR 의 diff 가 9 개 Template × 수십 개 파일로 거대해집니다. 시각 회귀 검증을 9 개 Template 에 동시에 해야 하고, 리뷰어가 무엇이 의도된 변화이고 무엇이 사고인지 구분하기 어렵습니다. cafe-default 한 개에만 적용한 demo 로 패턴을 굳히고, 나머지 8 개는 각각 다른 이유로 손볼 때 자연스럽게 옮기는 게 어떨까요?"

"미완성 상태가 한참 지속되는 거 아니야? 두 패턴이 동시에 살아 있는 게 더 헷갈리지 않을까?"

"그게 진짜 trade-off 입니다 — 두 패턴 공존의 인지 비용 vs 거대한 일괄 마이그의 리스크. 핵심 안전판 한 줄을 추가하면 됩니다: 새 Template 를 Generate 로 만들 때는 무조건 rich 패턴으로 출력한다. 그러면 마이그 부담이 늘지 않습니다."

이 결정이 ADR-0005 (Rich Design Tokens — 점진적 마이그레이션) 로 박제됐다. 지금도 9 개 중 1 개만 rich 패턴이지만, 그게 미완성 이 아니라 의도된 점진 전환 이라는 사실이 ADR 한 장으로 명문화되어 있다.

왜 이 단계가 가장 중요했나 META

처음엔 AI 가 내놓는 제안의 의도를 자주 못 알아들었다. "왜 이렇게 만들지?" 가 첫 반응이었고, 그래서 grill 단계에서 나는 끊임없이 왜? 와 대안은? 을 물었다. 점점 명확해진 건 두 가지였다.

(1) AI 제안에는 항상 reasoning 이 있다. 그걸 표면 답만 보고 채택하거나 거절하면, 다음에 같은 결정을 다시 해야 한다. reasoning 까지 이해해야 ADR 한 장으로 박제할 수 있고, 박제해야 다음 세션의 AI 에게도 같은 컨텍스트가 전달된다.

(2) Trade-off 는 둘 중 하나가 절대 우월하지 않다. DRY vs isolation, 일괄 마이그 vs 점진 마이그 — AI 는 항상 "왜 이쪽을 택했는지" 와 "다른 쪽이 더 맞는 상황은 언제인지" 를 같이 설명할 수 있다. 내 역할은 이 프로젝트의 상황에서 어느 쪽이 더 맞는지 판단 하는 것이었다 — 그건 외주할 수 없는 일이다.

STEP 3 · CONTEXT.md

어휘를 고정시키면 AI 가 흐트러지지 않는다

AI 는 영어 동의어 (theme / template, block / section, slug / domain) 에 쉽게 흔들린다. CONTEXT.md 의 글로서리 + Flagged ambiguities 섹션은 그 흔들림을 막는 단단한 닻이다.

한 용어가 두 가지를 가리키면, 이름을 둘로 쪼갠다 CONTEXT.md · Flagged ambiguities

다음은 모두 CONTEXT.md 의 "Flagged ambiguities" 섹션에서 명시적으로 분리된 어휘다. 각 항목은 한때 같은 단어로 두 가지를 가리켜서 혼선을 낳았던 흔적이다.

"theme" → Template / Category 로 분리. 옛 이름은 한 단어로 (1) 한 디자인과 (2) 그것이 속한 분류 버킷을 동시에 의미했다. migration 013 에서 themeKey → templateKey rename, PR #19 에서 디렉터리 구조를 src/templates/<category>/<leaf>/ 로 재배치하며 둘을 분리했다. 이제 옛 PR 을 읽을 때 "theme" 을 mental translate 한다.

"domain" 은 세 가지 다른 것을 가리킨다. (1) 사용자가 publish 하는 서브도메인 슬러그, (2) Clean Architecture 의 도메인 레이어, (3) 미래의 BYO 커스텀 호스트네임. 제품 컨버세이션에서는 (1) 을 항상 Subdomain 으로 부른다. (2) 는 구현 jargon, (3) 은 아직 canonical 이름이 없으므로 그 기능이 테이블에 오를 때 정한다.

"publish" 도 두 가지다. (1) 사용자가 자기 Site 를 draft → Live 로 바꾸는 행위 = Publish. (2) 어드민이 코드 Preset 을 Sync 해서 카탈로그에 새 Template 을 노출하는 행위 = Sync. 코드 권한 이름 canPublishTemplates 는 이 분리 이전에 정해진 잔재라 그대로 둔다 — 하지만 글로서리는 명확히 둘로 갈라놓는다.

"composition" 은 별도 도메인 개념이 아니다. 코드 곳곳 (RenderComposition, propose_composition) 에서 등장하지만, 본질은 그냥 한 Page 의 ordered Section list 다. 회화에서는 항상 "the Page's Sections" 라고 쓴다. AI 가 "composition" 을 별개 엔티티처럼 다루려는 경향을 명시적으로 차단한다.

왜 _Avoid_ 가 중요한가 METHOD

글로서리의 각 용어에는 정의뿐 아니라 _Avoid_ 항목이 있다. 예:

Site: A user's own editable, publishable website — created from a Template
       and owned by one User.
_Avoid_: UserSite (internal/DB name only), user-site, project, page
         (a Site contains Pages).

"이걸 쓰지 마" 가 "이걸 써" 만큼 중요한 이유: AI 가 글로서리 단어를 못 떠올리면 영어권 동의어를 자유롭게 끌어다 쓴다 (project, page, user-site). 그러면 같은 코드베이스 안에 동의어 4 개가 공존하면서 검색이 깨지고 다음 세션의 AI 가 또 다른 동의어를 가져온다. _Avoid_ 항목은 그 균열을 grill 단계에서 즉시 잡아낸다 — "이 단어 쓰면 안 되는데?".

글로서리를 갱신하는 트리거 OPERATION

이 프로젝트에서 글로서리 항목이 추가되거나 수정된 순간은 항상 다음 셋 중 하나였다.

(a) 어떤 단어를 자꾸 다르게 쓰고 있다는 걸 grill 단계에서 발견 → 정의 추가 + _Avoid_ 명시.

(b) 코드에서 rename 이 일어남 (themeKey → templateKey) → 글로서리에 "옛 이름" 을 Flagged ambiguities 에 박제 + 다음 세션이 옛 코드를 읽을 때 mental translation 가이드 제공.

(c) 새 도메인 개념이 등장 (예: array Field) → 정의 + 관계도 갱신.

한 번 박제된 이후로는 그 결정을 다시 토론하지 않는다. 이게 글로서리의 진짜 가치 — 같은 합의를 두 번 만들지 않게 해주는 비용 절감.

STEP 4 · ADR

중요한 trade-off 는 6 개 ADR 로 박제됐다

한 줄 결정만 적힌 가벼운 ADR. "왜 다른 길이 아닌 이 길이었나" 를 다음 세션의 AI 가 한 화면에 읽도록 만들기 위한 것.

ADR 결정 박제한 trade-off
0001
β-isolation		 Template 간 코드 공유 0tokens / components / css — Template 마다 자기 사본을 가짐. DRY (재사용) vs isolation (새 Template 추가의 자유). "같은 Hero 가 9 곳에 복제됐는데 추출해야 하지 않나" 라는 미래 PR 제안은 이 ADR 을 근거로 거절한다 — 의도된 중복.
0002
code = truth		 Template 의 source of truth 는 코드DB 는 sync 가 반영하는 read-side. template_json 은 항상 코드값으로 덮어씀. DB-as-truth (어드민이 빠르게 손봄) vs code-as-truth (Generate 워크플로우 전제, 코드 리뷰 게이트 보장). AI Generate 는 코드 파일로 떨어지고, 사람 리뷰 + Sync 두 단계를 거쳐야 카탈로그에 진입한다 — production 에 직접 쓰는 빠른 경로를 의도적으로 닫았다.
0003
Reserve-Confirm		 Asset 업로드는 Reserve-Confirm + 일일 orphan sweepinitUploadAction (pending) → 직접 업로드 → confirmUploadAction (active). 고아는 cron 이 일일 정리. 완벽한 정합성 (synchronous 검증) vs 실용적 정합성 (네트워크 단절 / 세션 만료 / 창 닫힘 시 orphan 을 사후 회수). 파일명에 남은 "two-phase" 는 정확하지 않다 — 2-Phase Commit 과 다르다. ADR 첫 줄에 명시.
0004
OCC-RPC		 UserSite 저장은 save_site_template_with_lock RPC 만 사용expectedUpdatedAt 검사 → STALE_VERSION 반환 시 Conflict modal. silent overwrite (가장 무서운 잠재 버그 — 다른 탭의 변경분이 며칠 후에야 사라진 게 발견됨) vs 명시적 충돌 노출. 새 저장 경로 (자동 정리 / 마이그 스크립트 등) 추가 시 RPC 우회 금지 — ADR 의 "Warning for future contributors" 섹션이 다음 세션에 직접 경고한다.
0005
gradual-migration		 Rich Design Tokens 는 cafe-default 부터 점진 전환현재 9 개 중 1 개만 적용. Generate 출력은 무조건 rich 패턴. 일괄 마이그 (한 PR 에 9 Template × 수십 파일) vs 점진 전환 (두 패턴 공존의 인지 비용). 안전판: 신규 Generate 는 무조건 rich 출력 → 마이그 부담이 새로 늘지 않음.
0006
capability-split		 canPublishTemplates 는 admin role 과 분리사용자 모더레이션 권한 ≠ 카탈로그 publish 권한. 단순한 역할 모델 (admin = 다 가능) vs 사고 차단 (운영자가 사용자 사이트 모더레이션 중 실수로 미완성 Template 을 publish 하는 시나리오). 이름 canPublishTemplates 는 분리 이전에 정해져 publish overload 가 발생하지만, 코드 호환성 때문에 유지 — Flagged ambiguities 에 박제.

ADR 의 진짜 효과 — Reference 가 PR / 코드에서 살아난다

ADR 은 박제된 채로 끝나지 않는다. 코드, 문서, PR 본문에서 반복적으로 인용되며 다음 세션의 AI 에게도 같은 컨텍스트를 주입한다.

실제 코드 / 문서에서의 ADR 인용 grep "ADR-" 의 일부 결과 
// CLAUDE.md — "DRY 보다 isolation 우선"
This is deliberate (isolation > DRY — see [ADR-0001](./docs/adr/0001-beta-model-template-isolation.md)).

// CLAUDE.md — auto-save 경로 가이드
When adding new save paths, always thread `expectedUpdatedAt` through
— never bypass the RPC (silent overwrites are the failure mode this prevents).
                                                              // ADR-0004

// docs/TEMPLATE_SYSTEM.md — 함정 #15
Optimistic concurrency RPC 우회 금지 (ADR-0004).
새 저장 경로 추가 시 expectedUpdatedAt 을 받아서 RPC 로 흘려야 함.

// CONTEXT.md — Site 정의 안에서도 ADR 링크
Persists edits through an optimistic-concurrency RPC that rejects stale
writes (see [ADR-0004](./docs/adr/0004-optimistic-concurrency-via-rpc.md)).
효과 · 다음 세션의 AI 가 어디서부터 읽기 시작해도 (코드, CLAUDE.md, 글로서리, TEMPLATE_SYSTEM.md, ADR 자체) 같은 결정에 도달한다. 단일 진실, 여러 진입점.
STEP 5 · /to-issues

AI 가 잡기 좋은 단위로 분해한다

한 번에 큰 작업을 던지면 AI 의 출력은 검토 불가능한 양이 된다. tracer-bullet vertical slice — end-to-end 로 동작하되 일부 단계만 stub — 으로 쪼개면 각 PR 이 작고 검토 가능해진다.

Tracer 시리즈 — AI Template Generation 파이프라인을 8 개로 쪼갠 사례

자연어 brief 한 줄로 새 Template 코드를 통째로 만드는 파이프라인. 한 PR 에 다 넣지 않고 "Tracer #1 = 전체 plumbing + 모든 단계 stub" 부터 시작해서, 다음 PR 들이 한 stub 씩 실제 LLM 호출로 교체했다.

Tracer #1ready-for-agent

스켈레톤 CLI + stub end-to-end

pnpm template:generate "<brief>" 진입점. 4-stage 호출 (propose_composition → propose_design_tokens → generate_section → validate_and_capture) 이 모두 하드코딩 stub 으로 돌지만 파일 생성 → codegen → preview 까지 동작.

Tracer #2ready-for-agent

propose_composition 을 실제 LLM 호출로

stub 을 Claude API 호출로 교체. brief → category + leaf 후보 + section 시퀀스. 카테고리 정규화 룰 / leaf slug 컨벤션 / 카테고리별 섹션 역할을 시스템 프롬프트에 명시.

Tracer #3ready-for-agent

propose_design_tokens 을 실제 LLM 호출로

2-layer 토큰 모델 (defaultGlobalStyles + designTokens, ADR-0005) 그대로 출력. Zod 가 hex 색 형식 / CSS length / 카테고리별 mood 가이드 검증.

Tracer #6ready-for-agent

Unsplash/Pexels 이미지 fetch 헬퍼

AI 가 image query 만 결정하고 헬퍼가 fetch + Supabase Storage 호스팅. pool offset random 으로 "AI 가 매번 1번 사진" 문제 회피.

Tracer #7ready-for-agent

validate_and_capture — 통합 게이트

tsc / eslint / validateTemplateJson / inline-tokens 스캔 / dataSchema↔JSX cross-check / Playwright 캡처 — 6 단계 모두 통과해야 LLM 출력이 받아들여짐.

Tracer #8ready-for-agent

new-category 승인 게이트

LLM 이 신규 카테고리를 제안하면 명시적 [y/N] 게이트 + 슬러그 가드 (^[a-z][a-z0-9-]{0,39}$). 거부 시 즉시 abort, LLM 재시도 X.

왜 stub 부터 시작했는가

처음엔 의아했다. "어차피 stub 인데 파일까지 다 만들면 의미가 있나?" 그런데 Tracer #1 의 acceptance criteria 를 읽으면 답이 나온다 — Tracer #1 의 진짜 목적은 "실제 LLM 비용 없이 인프라 plumbing 을 검증" 하는 것이었다. 인터랙티브 승인 UX, 파일 시스템 layout, codegen 등록 훅, validate hook, sync 흐름 — 이 모든 게 LLM 출력에 의존하지 않고 동작하는지 먼저 확인한 것.

이걸 깨달은 다음부터, 큰 기능을 받을 때마다 자동으로 묻게 됐다 — "이 작업의 첫 PR 은 무엇이 stub 이고 무엇이 real 이어야 하나?"

또 다른 분해 — Issue #22 (371 건 위반 정리)

토큰 enforcement ESLint 룰을 도입하면서 (Issue #8) 기존 코드에서 371 건의 위반이 발견됐다. 이 정리 작업을 한 PR 로 묶지 않고 카테고리별 8 개 PR 로 쪼갰다 — cafe → corporate → fitness → wedding → interior → medical → legal 순서로. 이유는 두 가지였다.

(1) 시각 회귀를 한 Template 씩 검증 가능. 한 번에 9 개를 바꾸면 어느 변경이 어느 페이지를 망가뜨렸는지 추적할 수 없다.

(2) 패턴이 PR 마다 정제됐다. 처음 cafe PR 에서 잡힌 false-positive 가 #25 의 rule fix 로 이어졌고, #26 에서 report-all fix, #27 에서 CSS-wide-keyword fix 가 추가됐다. 한 번에 모두 마이그했다면 ESLint 룰의 결함들이 검토 후반에 발견되어 처음부터 다시 작업하는 사태가 벌어졌을 것이다.

모든 정리가 끝난 #29 에서야 severity 를 'warn' → 'error' 로 승급. 이후 회귀는 pnpm lint 에서 즉시 차단된다.

STEP 6 · GUARDS

non-deterministic 한 AI 출력을 deterministic 으로 가두는 5 계층

AI Generate 파이프라인은 매번 다른 코드를 만든다. 하지만 그 출력이 받아들여지는 조건 은 매번 같다. 아래 5 계층 중 하나라도 fail 하면 stop — 사람이 인계받는다.

1

Zod schema — LLM 출력의 형식을 강제

scripts/lib/llm.ts 의 claudeJSON(systemPrompt, userMessage, schema) 헬퍼. Anthropic API 의 structured output 을 받자마자 Zod 가 검증한다. hex 색 정규식, CSS length, 카테고리 슬러그 패턴 (^[a-z][a-z0-9-]{0,39}$) 등이 schema 차원에서 실패하면 그 출력은 절대 파일로 떨어지지 않는다.

2

Per-stage human approval — [y/r/n] 게이트

Generate 파이프라인의 4 단계 (propose_composition, propose_design_tokens, generate_section, validate_and_capture) 각각에서 승인 / 재생성 / 거부 게이트가 멈춘다. --auto-approve 플래그가 있긴 하지만 그건 CI / smoke 용. 사람이 운영하는 일반 모드에서는 매 stage 마다 출력 보고 reasoning 검증 후 다음으로 넘어간다.

3

New-category gate — 슬러그 가드

LLM 이 추출한 카테고리가 기존 src/templates/<category>/ 에 없으면 명시적 [y/N] 게이트. 정확 일치만 받아 fuzzy 매칭 안 함 (cafe-studio 는 cafe 와 별개로 취급). 슬러그 가드 위반 시 LLM 재시도 X — brief 를 다시. 왜? 카테고리는 카탈로그 구조에 영향을 주는 결정이고, 사람의 명시적 승인 없이 늘어나면 분류 체계가 흐트러진다.

4

validate_and_capture — 6 단계 통합 게이트

최종 단계. (1) tsc --noEmit, (2) eslint <templateRoot> (no-inline-design-tokens 포함), (3) validateTemplateJson (15 종 error code), (4) validateTemplateFiles (file-level 인라인 색·폰트 스캔), (5) dataSchema ↔ JSX 일관성 cross-check (declared 필드 ↔ getFieldValue 참조 매칭), (6) Playwright Chromium 썸네일 캡처. (1)–(5) 중 하나라도 실패하면 즉시 halt + 부분 진행물 워킹 트리에 남김 (retry 안 함 — 사람 인계가 맞음).

5

Sync 단계의 두 번째 validate + 어드민 2-step Preview/Apply

코드가 머지된 뒤 pnpm template:sync 가 다시 한 번 validateTemplateJson 을 실행한다 (이번엔 availableTemplateKeys 옵션 포함). DB 에 반영되는 마지막 순간까지 같은 룰이 적용된다. 어드민 UI 는 추가로 2-step (Preview → Apply) 을 강제하고, Apply 는 canPublishTemplates 권한 (ADR-0006) 으로 분리된 권한만 가능.

Validate 룰 카탈로그 — non-deterministic 을 정의한 곳

계층 4 의 핵심. AI 가 만든 출력이 도메인 규칙을 어기지 않았는지 검증.

src/lib/template/validate.ts — error code 일부 block (error) / pass-with-warn (warning) 
// Section / Field 검증

FIELD_TYPE_MISMATCH       field.type ≠ schema[field].type
DUPLICATE_PAGE_SLUG       페이지 간 slug 중복
DUPLICATE_SECTION_ID      페이지 내 section.id 중복

// Array Field (반복 항목) 검증
MISSING_ITEM_SCHEMA       type: 'array' 인데 itemSchema 정의 안 됨
NON_ARRAY_FIELD_VALUE     type: 'array' 인데 items 가 배열 아님
ARRAY_ITEMS_BELOW_MIN     minItems 위반
ARRAY_ITEMS_ABOVE_MAX     maxItems 위반

// 시각 토큰 위반 (Generate 파이프라인 file-level 스캔)
INLINE_COLOR_LITERAL      #rgb / #rrggbb / rgb() / hsl() 인라인 사용

핵심 약속 · 이 룰들을 두 군데 에 동시에 둔다 — Generate 시점 스캔 (validateTemplateFiles) 과 ESLint custom rule (no-inline-design-tokens). regex / whitelist 가 의도적으로 중복돼 있고, "한쪽 바꾸면 다른 쪽도 바꿔" 라는 코멘트가 두 파일 모두에 박혀 있다. 한쪽만 새지 않게 하기 위한 안전판.
eslint-rules/no-inline-design-tokens.mjs — Custom ESLint rule AST 기반 (Literal / TemplateElement / Property fontFamily) 
// 인라인 색 리터럴 차단. var(--*) 토큰만 허용.
// whitelist: transparent, inherit, currentColor, none, initial, unset, revert
// (CSS 키워드 — 디자인 토큰이 아님)

const COLOR_HEX_RE  = /#(?:[0-9a-fA-F]{8}|[0-9a-fA-F]{6}|[0-9a-fA-F]{4}|[0-9a-fA-F]{3})(?!\w)/g;
const COLOR_FUNC_RE = /\b(?:rgb|rgba|hsl|hsla)\s*\(/g;
const FONT_FAMILY_CSS_RE = /font-family\s*:\s*['"][^'"\n]+['"]/gi;

return {
  Literal(node)        { if (typeof node.value === 'string') checkString(node, node.value); },
  TemplateElement(node) { checkString(node, node.value?.cooked ?? ''); },
  Property(node)       { /* JSX inline style: { fontFamily: '...' } */ },
};
운영 · severity 는 'error'. Issue #22 에서 누적 위반 371 건을 카테고리별 8 PR 로 정리한 뒤 승급됐다. 이제 pnpm lint 가 새 인라인 hex 를 즉시 차단한다 — Generate 가 만든 코드든 사람이 짠 코드든.
STEP 7 · 개발자의 역할

AI 가 짤 수 있는 것 vs 사람이 해야 하는 것

이 프로젝트에서 내가 한 일은 "AI 가 만든 코드를 받아쓰기" 가 아니라 "AI 가 만든 reasoning 을 검증하고 채택 / 거절하기". 실제로 채택한 사례, 거절한 사례, 처음에는 의도를 못 읽어 헤맸던 사례를 정리한다.

처음에는 AI 제안의 의도를 못 알아들었다 — "왜 굳이 이렇게?" 가 첫 반응
예: AI 가 RenderComposition 을 별도 컴포넌트로 추출하자고 했을 때, "그냥 Template index.tsx 안에 인라인으로 두면 안 되나?" 가 첫 반응이었다. grill 끝에 이유가 드러났다 — RenderComposition 은 어드민 CompositionPreview, 사용자 에디터 preview, Live 사이트 렌더 세 곳에서 동시에 쓰는 공통 패스 라서 분리해야 한다.

같은 패턴이 여러 번 반복됐다. AI 가 어떤 구조를 제안할 때, 그 구조가 어디서 다시 호출되는지 를 묻는 게 습관이 됐다. "왜 이렇게?" 가 grill 의 가장 좋은 시작 질문이다.
AI 제안을 그대로 채택한 사례 — Reserve-Confirm 명명 caveat
Asset 업로드 패턴을 처음 도입할 때 나는 자연스럽게 "two-phase" 라고 불렀다. 분산 시스템 용어가 머릿속에 있어서. AI 가 ADR 초안을 쓸 때 "파일명에 남은 two-phase 는 작성 시점 용어. 정확한 명칭은 Reserve-Confirm (init = reserve, confirm = activate). 분산 트랜잭션 프로토콜인 2-Phase Commit (2PC) 과는 다르다." 라는 첫 줄을 제안했다.

나는 처음엔 "그게 그거 아닌가?" 싶었지만, 2PC 는 두 노드가 합의에 도달하는 분산 프로토콜이고 이건 단일 노드의 두 단계 상태 전환이라는 걸 다시 들었다. 파일명을 바꾸는 건 비용이 컸지만 ADR 첫 줄에 명시하는 것만으로 충분했다 — 다음 세션의 AI 가 이걸 2PC 와 혼동하지 않는다. 그게 핵심.
AI 제안을 거절한 사례 — "Sync 의 진실 source 를 DB 로 옮기자"
한 번은 AI 가 "Sync 가 코드 → DB 방향만 가는 게 번거롭다. DB 가 truth 이고 어드민에서 자유롭게 편집할 수 있게 하자" 고 제안했다. DRY 한 길로 보였다 — Generate 도 직접 DB 에 쓰고, 어드민도 직접 편집하고.

하지만 grill 끝에 거절했다. 이유는 두 가지 —
(1) 코드 리뷰 게이트. 코드가 진실이면 Generate 결과물이 PR 로 떨어지고 사람이 reviewable 한 diff 로 본다. DB 로 바로 가면 그 게이트가 사라진다.
(2) 재현성. 코드는 git history 로 재현되지만 DB 상태는 어드민 손에 따라 변한다. 다른 환경 (staging / 새 prod) 에 같은 Template 를 깔려면 코드 truth 가 훨씬 안전하다.

이 결정이 ADR-0002 로 박제됐다. 한 줄 핵심: "코드와 DB 가 다른데 어디가 맞나" 라는 질문의 답은 항상 코드.
AI 제안의 reasoning 을 검증한 결과 일부만 채택한 사례 — Optimistic Concurrency
에디터 저장에 동시성 제어가 필요해졌을 때 AI 가 세 옵션을 제시했다 — (1) pessimistic lock, (2) optimistic with version column, (3) optimistic with updated_at timestamp.

AI 의 첫 추천은 (2) — version 컬럼이 명시적이고 직관적이라는 이유. 하지만 grill 끝에 (3) 으로 갔다.
이유 — 이 프로젝트의 다른 모든 row 가 이미 updated_at 을 갖고 있다. version 을 새로 추가하면 마이그레이션 + 기존 데이터 백필 + 두 개의 의미 비슷한 컬럼이 공존하는 비용이 생긴다. timestamp 충돌은 같은 millisecond 가 아니면 일어나지 않고, 멀티탭/멀티디바이스 시나리오에서는 충돌 간격이 항상 ms 이상이다.

AI 의 추천이 항상 맞는 건 아니지만, 세 옵션의 trade-off 를 제대로 설명한 건 사람이 못 했을 정도로 빨랐다. 마지막 판단만 내가 한 것.
workflow 자체를 운영하면서 배운 것 — 가장 비싼 비용은 "잊혀짐"
프로젝트 초반에 ADR 없이 결정한 사항들이 두세 세션 뒤에는 다시 토론 대상이 됐다. AI 는 매 세션 깨끗하게 시작하고, 나도 한 달 전 결정의 이유를 정확히 기억하지 못한다.

가장 비싼 비용은 같은 결정을 두 번 만드는 비용 이었다. ADR 한 장 (보통 5~10 줄) 을 쓰는 데 5 분 걸리지만, 그게 없으면 같은 trade-off 를 다음 세션에서 다시 30 분 토론한다.

그래서 지금은 grill 단계에서 결정이 굳는 순간 자동으로 묻는다 — "이거 ADR 한 줄 가치 있나?"
값 있는 경우의 시그널: (a) 다음 세션의 AI 가 이 정보 없이 다른 답에 도달할 가능성이 있다 / (b) DRY 같은 본능적 제안을 거절해야 하는 trade-off 다 / (c) 한 줄로 미래 PR 제안을 거절할 근거가 된다.
"AI 가 많이 짰다" 가 아니라 — workflow 가 일관성을 만든다
이 프로젝트의 Template 9 개, ADR 6 개, SQL migration 12 개, Server Action 수십 개 — 거의 모든 코드가 AI 와의 협업으로 만들어졌다. 하지만 그 결과물이 일관된 건 AI 가 똑똑해서가 아니다.

일관성을 만든 건 workflow — 매 변경이 grill → CONTEXT/ADR → /to-issues → branch → validate → review → merge 를 통과한다는 사실.
이 루프에서 AI 는 제안하고, 코드 짜고, 검증 룰 통과 여부를 알려주는 역할. 사람은 reasoning 해석, trade-off 판단, 도메인 언어 유지, 결정 박제.

실제로 "AI 가 다 짰다" 라고 말하면 핵심을 놓친다. 코드는 AI 가 짤 수 있어도, 어떤 코드가 이 프로젝트의 일관성에 맞는지 판단하는 일은 사람만 할 수 있다. 그 판단을 시스템에 박제 (ADR / 글로서리 / validate 룰 / ESLint 룰) 해놓으면, 다음 세션의 AI 도 같은 판단을 한다.
