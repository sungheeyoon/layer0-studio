이미지 업로드 파이프라인
Reserve-Confirm + Orphan Sweep

클라이언트가 스토리지에 직접 업로드하면서도 DB·Storage 정합성을 잃지 않기 위한 2단계 등록(pending → active)과 SKIP LOCKED 기반 비동기 회수 패턴.

TL;DR · 한눈에

30초 요약

⚠ 문제
서버 프록시는 대역폭·타임아웃 부담, 그냥 client → storage는 업로드 중단 시 storage에만 파일이 남음 (orphan)
🛠 해결
init에서 pending row 예약 → 클라이언트가 직접 업로드 → confirm으로 active 마킹. 누락분은 cron + SKIP LOCKED 큐로 비동기 회수
✓ 결과
서버 대역폭 0, DB ↔ Storage 정합성 자가 복구, 멀티 워커가 같은 항목을 두 번 처리하지 않음

STEP 2 · 핵심 아이디어

"상태 머신 + 자가 복구"로 푼다

자산은 두 상태만 가진다. 미사용 자산은 1시간 후 큐로 보내져 회수된다.

자산 상태 머신

pending
init으로 예약된 상태. 메타데이터 (user, size, mime) 만 DB에 있고, 스토리지엔 아직 파일이 없거나 업로드 중.
→ confirm
active
클라이언트 업로드 성공 후 confirm으로 확정. Section의 image Field에서 참조 가능.

자가 복구를 위한 RPC 두 개

sweep_orphaned_assets()
생성된 지 1시간이 지났는데 어떤 asset_usages에서도 참조되지 않는 자산을 찾아 cleanup_queue에 enqueue. ON CONFLICT DO NOTHING으로 중복 enqueue 차단.
claim_cleanup_task()
SELECT … FOR UPDATE SKIP LOCKED LIMIT 1으로 큐에서 한 건을 원자적으로 점유. 여러 워커가 동시 실행돼도 같은 항목을 중복 처리하지 않음.
STEP 3 · 실제 동작 흐름

7단계 프로세스

클라이언트 서버 액션 스토리지 DB (Postgres) Cron / Worker
1
CLIENT

사용자가 이미지 선택

에디터에서 image Field 클릭 → 파일 picker → File 객체 확보 (filename, mimeType, size).

2
SERVER

initUploadAction — 검증 + pending row 예약

validateAssetInfo로 MIME / size 검증 통과 시 assets에 status='pending' row 생성. { assetId, uploadPath } 반환.

3
STORAGE

클라이언트가 직접 Supabase Storage에 PUT

서버를 거치지 않고 uploadPath로 바로 업로드. 서버 함수의 대역폭 / 타임아웃 제약을 우회.

4
SERVER

confirmUploadAction — active 마킹

소유권 (asset.userId === user.id) 검증 후 status='active'로 갱신, public CDN URL 반환.

5
CLIENT

Section Field에 URL 반영

받은 URL을 image Field에 set. 동시에 asset_usages에 (asset_id, site_id, slot_key) 기록 → 어느 사이트의 어느 자리에서 쓰이는지 추적 가능.

6
CRON

매일 03:00 UTC — sweep_orphaned_assets

/api/cron/cleanup-assets가 호출. 생성된 지 1h 이상이면서 asset_usages에 없는 자산을 cleanup_queue에 enqueue. (Hobby plan 1 cron/day 제약 — ADR-0003)

7
WORKER

claim_cleanup_task — 큐 소비 + 삭제

SKIP LOCKED로 한 건을 안전하게 점유 → Storage 파일 + DB row 삭제 → 큐 row done. 실패 시 retry_count 증가, 3회 초과 시 영구 보류.

STEP 4 · 핵심 코드

3개 레이어, 각각 한 조각씩

① 클라이언트 — init → upload → confirm ImageUploader.tsx 
// ① init — pending row 예약 + uploadPath 받기
const { assetId, uploadPath } = await initUploadAction({
  filename: file.name,
  mimeType: file.type,
  size:     file.size,
});

// ② Supabase Storage에 직접 업로드 (서버 우회)
const { error } = await supabase.storage
  .from('user_assets')
  .upload(uploadPath, file);

if (error) throw error;

// ③ confirm — active 마킹 + 공개 URL 수령
const { publicUrl } = await confirmUploadAction({
  assetId,
  uploadPath,
});

// ④ Section image Field에 반영
updateField(sectionId, fieldKey, publicUrl);
포인트 · 3단계 중 어느 곳에서든 실패해도 최악의 결과는 1시간짜리 orphan일 뿐. 부분 업로드는 큐가 회수한다.
② 서버 액션 — 두 시점만 관여 actions.ts 
export async function initUploadAction(input: InitInput) {
  return withUser(async (user, supabase) => {
    const useCase = createAssetUploadUseCase(supabase);
    return useCase.executeInit({ userId: user.id, ...input });
    // ↑ validateAssetInfo → insert pending row → return { assetId, uploadPath }
  });
}

export async function confirmUploadAction(input: ConfirmInput) {
  return withUser(async (user, supabase) => {
    const useCase = createAssetUploadUseCase(supabase);
    return useCase.executeConfirm({ userId: user.id, ...input });
    // ↑ 소유권 검증 → status='active' → return { publicUrl }
  });
}
포인트 · 서버는 예약과 확정 두 순간만 처리. 파일 자체의 흐름엔 관여하지 않아 함수 타임아웃·대역폭 비용 0.
③ Postgres RPC — SKIP LOCKED 작업 큐 008_cleanup_worker_rpc.sql 
-- 1) 1h 이상 미사용 자산을 큐에 enqueue (중복은 무시)
CREATE OR REPLACE FUNCTION sweep_orphaned_assets()
RETURNS SETOF UUID AS $$
BEGIN
  INSERT INTO cleanup_queue (asset_id)
  SELECT a.id FROM assets a
  WHERE a.created_at < now() - interval '1 hour'
    AND NOT EXISTS (
      SELECT 1 FROM asset_usages u WHERE u.asset_id = a.id
    )
  ON CONFLICT DO NOTHING;   -- ← 중복 enqueue 방지
END;
$$;

-- 2) 워커가 큐에서 한 건을 안전하게 점유
CREATE OR REPLACE FUNCTION claim_cleanup_task()
RETURNS TABLE (id UUID, asset_id UUID, ...) AS $$
BEGIN
  RETURN QUERY
  UPDATE cleanup_queue
  SET status = 'processing', updated_at = now()
  WHERE cleanup_queue.id = (
    SELECT q.id FROM cleanup_queue q
    WHERE q.status IN ('pending', 'failed')
      AND q.retry_count < 3
    ORDER BY q.created_at ASC
    FOR UPDATE SKIP LOCKED      -- ← 멀티 워커 안전
    LIMIT 1
  )
  RETURNING ...;
END;
$$;
포인트 · SKIP LOCKED는 잠긴 row를 대기 없이 건너뛰는 옵션. 여러 워커가 같은 큐를 동시에 폴링해도 충돌 없이 분산 소비된다.
STEP 5 · 설계 결정

주요 트레이드오프

각 결정의 배경과 검토했던 대안.

서버 프록시 대신 클라이언트 직접 업로드를 택한 이유
서버를 거치면 Serverless 함수의 메모리/타임아웃 한계 (Vercel 기본 ~4.5MB body, 300s)에 묶이고 대역폭이 두 번 (client → server → storage) 청구됩니다. Supabase Storage는 RLS와 owner 정책으로 직접 업로드를 안전하게 받을 수 있으므로, 서버는 검증·예약·확정 메타데이터만 다루는 게 합리적이었습니다.
왜 init / confirm 두 단계로 나눴나
단순 client → storage만으로는 업로드 메타데이터를 서버가 검증할 시점이 없습니다. init에서 MIME·size를 미리 검증해 잘못된 업로드를 차단하고, confirm에서 소유권을 한 번 더 검증해 다른 사용자의 path를 가로채는 시도를 막습니다. 양 끝에서 한 번씩 책임지는 구조.
advisory lock 대신 SKIP LOCKED를 쓴 이유
cleanup_queue는 본질적으로 작업 큐 (work queue)이고, advisory lock은 임의 키에 대한 mutual exclusion에 더 적합합니다. SELECT … FOR UPDATE SKIP LOCKED LIMIT 1은 큐 패턴의 표준 관용구로, 잠긴 row를 건너뛰며 다음 가능한 항목을 점유하기 때문에 워커가 늘어도 자연스럽게 분산됩니다. Postgres가 row-level lock으로 직접 보장하니 외부 락 매니저도 필요 없습니다.
cleanup_queue를 별도 테이블로 둔 이유
retry/실패 메타데이터 (retry_count, last_error) 를 자산 테이블과 섞고 싶지 않았습니다. UNIQUE(asset_id)로 중복 enqueue를 차단하면서 큐로서의 idempotency를 강제합니다. 자산 도메인과 정리 워커의 관심사가 다르므로 테이블도 분리.
1시간 TTL의 근거
업로드 후 사용자가 사이트에 적용하기까지 걸리는 시간을 고려한 grace period입니다. 너무 짧으면 정상 흐름을 깨고 (예: 업로드 → 다른 탭에서 작업 → 늦게 적용), 너무 길면 storage 비용이 누적됩니다. 1h는 단일 상수로 분리되어 있어 측정 후 조정 가능합니다.
매일 1회 cron의 한계
Vercel Hobby plan의 1 cron/day 제약 때문이며, 최대 24h 동안 storage에 orphan이 남을 수 있습니다 (ADR-0003). 유료 플랜으로 전환 시 스케줄만 시간당으로 바꾸면 코드 변경 없이 그대로 동작하도록 설계했습니다. 설계가 정책에 의존하지 않고 주기에만 의존하도록 분리한 것이 핵심.
현재 모델의 한계
가장 큰 한계는 "동일 자산을 여러 사이트에서 공유"하는 시나리오입니다. 지금은 asset_usages가 site_id별로 분리돼 있어 처리 가능하지만, 템플릿/스톡 이미지 같은 cross-tenant 공유 자산이 도입되면 별도 분류와 lifecycle이 필요합니다. 실제로 template_assets bucket (migration 014) 은 이미 별도 도메인으로 분리해 둔 상태.
