PORTFOLIO · TECHNICAL DEEP-DIVE

프레임워크 없는 의존성 주입
Clean Architecture, 작게 적용하기

Domain 레이어를 외부 의존성 0으로 유지하면서, NestJS·InversifyJS 같은 DI 프레임워크 없이 factory 함수와 인터페이스만으로 테스트 가능성과 교체 가능성을 확보한 방법.

TL;DR · 한눈에

30초 요약

⚠ 문제
비즈니스 규칙이 Supabase 클라이언트와 직접 결합되면 단위 테스트는 mock 지옥, 인프라 교체 시 코드 전반 수정 필요
🛠 해결
4-layer 분리 + 인터페이스 기반 repository + 요청별 factory 함수 DI (프레임워크 X). Domain은 무엇도 import하지 않음
✓ 결과
UseCase를 in-memory fake로 DB 없이 테스트, 인프라 변경 시 data 레이어만 수정. 학습 곡선 0 (TS 기본 문법만 사용)

STEP 2 · 왜 프레임워크 없이?

NestJS / Inversify vs Factory 함수

"DI = 프레임워크"라는 통념을 검토해 봤다. Next.js Server Action 모델에선 오히려 단순함이 이긴다.

관점 DI 프레임워크 (NestJS / Inversify) Factory 함수 (이 프로젝트)
wiring 코드 @Module / @Injectable / DI 컨테이너 빌드 한 줄 함수 — new Repo(supabase) → new UseCase(repo)
요청별 인스턴스 Request scope 설정 필요 (default = singleton) 자동 — 함수가 매 호출 새 인스턴스 생성
Next.js Server Action 호환 컨테이너 부팅·라이프사이클 별도 관리 호환 0 cost — action 함수 안에서 그냥 호출
학습 곡선 데코레이터·메타데이터·reflect-metadata TypeScript 기본 문법만
테스트 시 주입 교체 TestingModule.overrideProvider(...) new UseCase(fakeRepo) — 한 줄
적합한 상황 대형 백엔드, 깊은 의존성 그래프, 다양한 라이프사이클 2-3 layer, 요청-응답 모델, 작은 팀
STEP 3 · 요청 1건의 흐름

"사이트 JSON 저장" — 끝에서 끝까지

1
APP

클라이언트가 Server Action 호출

에디터가 saveSiteJsonAction(siteId, siteJson, expectedUpdatedAt) 호출.

2
DI

Factory가 의존성 wiring

createUpdateSiteJsonUseCase(supabase) → new SupabaseUserSiteRepositoryImpl(supabase) → new UpdateSiteJsonUseCase(repo). 요청별 fresh 인스턴스.

3
DOMAIN

UseCase가 비즈니스 규칙 실행

findById → ownership 검증 → JSON 구조 검증 → repository.updateSiteJson 호출. 실패 시 TemplateError(code) throw.

4
DATA

Repository가 Supabase RPC 호출

인터페이스를 만족하는 구현이 실제로 save_site_template_with_lock RPC 호출. 'STALE_VERSION' 반환 시 domain error로 변환해 throw.

5
APP

Server Action이 에러 코드로 변환

withUser 헬퍼가 domain error를 catch → { error: code } 형태로 반환. 도메인은 HTTP·i18n·직렬화를 알지 못함.

6
APP

클라이언트가 코드 → 한국어 매핑

src/lib/errors/messages.ts에서 'STALE_VERSION' → "다른 곳에서 먼저 저장됐습니다"로 매핑해 토스트 표시.

STEP 4 · 핵심 코드

4개 레이어, 각각 한 조각씩

① Domain — Repository 인터페이스 + UseCase domain/ 
// repositories/user-site.repository.ts
export interface IUserSiteRepository {
  findById(id: string): Promise<UserSite | null>;
  updateSiteJson(id: string, json: TemplateJson, expectedUpdatedAt?: string): Promise<UserSite>;
  // ... 외부 라이브러리 0개 import
}

// usecases/user-site/update-site-json.usecase.ts
export class UpdateSiteJsonUseCase {
  constructor(private repo: IUserSiteRepository) {}

  async execute(siteId: string, json: TemplateJson, userId: string, expectedUpdatedAt?: string) {
    const existing = await this.repo.findById(siteId);
    if (!existing)                  throw new TemplateError('SITE_NOT_FOUND');
    if (existing.userId !== userId) throw new TemplateError('SITE_ACCESS_DENIED');

    this.validateJson(json);
    return this.repo.updateSiteJson(siteId, json, expectedUpdatedAt);
  }
}
포인트 · UseCase는 IUserSiteRepository만 알고 Supabase는 모른다. 같은 인터페이스를 만족하는 어떤 구현이든 받아들일 수 있다.
② Data — Supabase Repository 구현 data/repositories/supabase-user-site.repository.impl.ts 
export class SupabaseUserSiteRepositoryImpl implements IUserSiteRepository {
  constructor(private supabase: SupabaseClient) {}

  async updateSiteJson(id: string, json: TemplateJson, expectedUpdatedAt?: string) {
    const { data, error } = await this.supabase.rpc(
      'save_site_template_with_lock',
      { p_site_id: id, p_new_json: json, p_expected_updated_at: expectedUpdatedAt },
    );
    if (data === 'STALE_VERSION') throw new TemplateError('STALE_VERSION');
    if (error)                    throw new TemplateError('UNKNOWN');
    return await this.findById(id) as UserSite;
  }
}
포인트 · 인프라 세부 (RPC 이름, 에러 형식) 가 여기에 격리. RLS·SQL 함수도 이 레이어 안에서만 신경 쓴다.
③ DI — Factory 함수 + Server Action 진입점 lib/di/container.ts & app/.../actions.ts 
// lib/di/container.ts — wiring을 한 군데로
export const createUpdateSiteJsonUseCase = (supabase: SupabaseClient) => {
  const repo = new SupabaseUserSiteRepositoryImpl(supabase);
  return new UpdateSiteJsonUseCase(repo);
};

// app/.../actions.ts — Server Action은 그냥 호출만
export async function saveSiteJsonAction(
  siteId: string, json: TemplateJson, expectedUpdatedAt?: string,
) {
  return withUser(async (user, supabase) => {
    const useCase = createUpdateSiteJsonUseCase(supabase);
    const site = await useCase.execute(siteId, json, user.id, expectedUpdatedAt);
    return { success: true, updatedAt: site.updatedAt };
    // withUser가 TemplateError를 catch해 { error: code } 로 변환
  });
}
포인트 · factory는 요청마다 호출되어 새 인스턴스를 만든다. Supabase 클라이언트가 쿠키 세션을 가지므로 싱글턴이 불가능하기 때문.
④ Test — In-memory fake로 DB 없이 검증 domain/__tests__/update-site-json.usecase.test.ts 
// fakes.ts — 인터페이스를 만족하는 in-memory 구현
export class FakeUserSiteRepo implements IUserSiteRepository {
  sites: UserSite[];
  constructor(initial: UserSite[] = []) { this.sites = [...initial]; }

  async findById(id: string) { return this.sites.find(s => s.id === id) ?? null; }
  async updateSiteJson(id: string, json: TemplateJson) {
    const site = this.sites.find(s => s.id === id)!;
    site.siteJson = json;
    return site;
  }
  // ... 인터페이스의 다른 메서드들
}

// .test.ts — Supabase 없이 UseCase만 검증
it('throws SITE_ACCESS_DENIED if user does not own the site', async () => {
  const repo = new FakeUserSiteRepo([makeSite({ userId: 'owner' })]);
  const uc   = new UpdateSiteJsonUseCase(repo);

  await expect(
    uc.execute('site-1', makeTemplateJson(), 'intruder'),
  ).rejects.toMatchObject({ code: 'SITE_ACCESS_DENIED' });
});
포인트 · 테스트는 UseCase의 행동만 검증한다. "어떤 mock 함수가 몇 번 호출됐는지"가 아니라 "주어진 입력에 어떤 결과/에러가 나오는지". 리팩토링에 강하다.
STEP 5 · 설계 결정

주요 트레이드오프

각 결정의 배경과 검토했던 대안.

NestJS · InversifyJS 같은 DI 프레임워크를 안 쓴 이유
Next.js Server Action 모델은 "한 요청 안에서 함수가 호출되고 끝나는 구조"입니다. 프레임워크가 제공하는 라이프사이클 관리·모듈 시스템·데코레이터는 그 모델 위에 얹기엔 부담만 큽니다. 실제 wiring 코드는 한 줄 (new Repo(supabase) → new UseCase(repo)) 이라 추상화 비용보다 직접 작성 비용이 더 작았습니다. 단, layer 수가 5+ 이상이거나 다양한 라이프사이클이 필요해지면 도입을 검토해야 합니다.
요청별 fresh DI (싱글턴 회피)
Supabase 클라이언트는 요청별 쿠키에서 세션을 읽어 빌드됩니다. 싱글턴으로 만들면 "다른 사용자의 세션을 가진 클라이언트"가 재사용될 수 있어 치명적입니다. factory 함수는 매 호출 시 새 인스턴스를 반환하므로 이 함정을 구조적으로 피합니다. 성능 부담은 객체 두세 개 생성 수준이라 무시 가능.
도메인 에러를 throw + Server Action에서 catch
Domain은 HTTP·i18n·직렬화 같은 전달 매체를 알아선 안 됩니다. UseCase가 TemplateError('SITE_NOT_FOUND')를 throw하면, Server Action의 withUser 헬퍼가 이를 catch해 { error: 'SITE_NOT_FOUND' }로 변환합니다. 클라이언트는 코드를 한국어 메시지로 매핑 (src/lib/errors/messages.ts). 책임이 세 곳에 깔끔하게 나뉩니다.
mock이 아닌 in-memory fake를 선택한 이유
Mock은 "이 함수가 이렇게 호출됐는지"를 검증해 구현 세부에 묶이고 (brittle test), Fake는 "이 입력에 이 결과가 나오는지"를 검증해 동작에 묶입니다. UseCase 내부 호출 순서를 바꾸는 리팩토링이 mock 테스트는 깨뜨리지만 fake 테스트는 깨지 않습니다. 도메인 인터페이스가 작고 명확하기에 fake 작성 비용도 작음.
어디까지 분리했고 어디는 안 했나
분리한 것 · 비즈니스 규칙 (ownership, JSON 검증), 에러 코드, repository 인터페이스. 인프라 교체가 *가능하게* 설계됨.

분리하지 않은 것 · Supabase RLS 정책, RPC 함수 (save_site_template_with_lock) 의 구체적 시그니처는 data 레이어 안에서만 존재. 인터페이스 차원에서 추상화하지 않았는데, 그렇게 하면 인터페이스가 무한히 비대해질 뿐 실제 교체 시나리오가 없기 때문. "가능하게"와 "실제로 할 것"을 구분한 결과.
현재 모델의 한계와 적용 범위
잘 맞는 상황 · 요청-응답 기반 (Server Action, REST), 의존성 그래프가 2-3 layer, 작은 팀.

한계 · 백그라운드 워커·이벤트 기반 시스템처럼 라이프사이클이 복잡해지면 factory만으로 부족. cron worker, queue consumer 등이 도입되면 그 부분만 부분적으로 컨테이너 (또는 명시적 builder) 를 도입할 가능성 있음. 처음부터 큰 구조를 도입하는 대신, 필요한 시점에 정확히 필요한 만큼 도입하는 것이 이 코드베이스의 일관된 원칙.
