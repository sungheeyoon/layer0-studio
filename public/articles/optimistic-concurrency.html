낙관적 동시성 제어
(Optimistic Concurrency Control)

자동 저장이 있는 에디터에서 동시 편집으로 인한 silent overwrite를 어떻게 감지하고 막았는지에 대한 이야기.

TL;DR · 한눈에

30초 요약

⚠ 문제
4초 자동 저장 + 멀티 탭/디바이스 → 먼저 저장한 변경분이 silent하게 덮어써짐 (Last-Write-Wins)
🛠 해결
클라이언트가 "내가 본 버전(updated_at)"을 토큰으로 들고 다님 → 서버가 RPC에서 비교해 다르면 STALE_VERSION 반환
✓ 결과
충돌 감지 시 모달로 사용자에게 결정권 위임 (Reload / Keep Editing) — 데이터 손실 0
STEP 1 · 문제 인식

왜 이게 필요했을까?

자동 저장을 켜는 순간 발생하는 시나리오. 멀티 디바이스가 아니라 같은 브라우저의 두 탭만으로도 발생한다.

STEP 2 · 핵심 아이디어

"버전 토큰"으로 막는다

클라이언트가 자기가 본 마지막 updated_at을 들고 다니다가 저장할 때 함께 보낸다. 서버는 DB의 현재 값과 비교해서 다르면 거부.

✗ 충돌 케이스 — 다름

→

2026-05-15 10:01:04
≠

STEP 3 · 실제 동작 흐름

7단계 프로세스

클라이언트 서버 액션 DB (Postgres RPC)
1
CLIENT

로딩 시 버전 토큰 기억

에디터가 마운트될 때 knownUpdatedAtRef = site.updatedAt으로 "내가 본 버전" 저장.

2
CLIENT

편집 감지 → 4초 디바운스

필드를 수정하면 isDirty = true 설정 후 4초 타이머 시작. 4초 안에 또 수정하면 타이머 리셋.

3
CLIENT

beforeunload 가드

아직 저장 안 된 상태(isDirty)에서 탭 닫으면 브라우저 기본 경고. 디바운스 윈도우 내 닫힘 방지.

4
SERVER

저장 요청 (토큰 동봉)

4초 후 saveSiteJsonAction(siteId, json, knownUpdatedAt) 호출. 토큰이 같이 전송됨.

5
DATABASE

RPC: 락 + 비교 + 갱신 (atomic)

FOR UPDATE로 행 잠그고 updated_at 비교 → 다르면 'STALE_VERSION' 반환, 같으면 JSON 갱신 후 'OK' 반환.

6
CLIENT

응답 분기

✓ 성공이면 knownUpdatedAtRef를 새 값으로 회전.
✗ STALE_VERSION이면 충돌 모달 띄움.

7
CLIENT

사용자 결정

Reload → 최신 버전 다시 받기 (내 변경분 폐기)
Keep Editing → 모달 닫고 계속 편집 (다음 저장 때 또 충돌 가능)

STEP 4 · 핵심 코드

3개 레이어, 각각 한 조각씩

① 클라이언트 — 토큰 들고 다니기 DynamicEditor.tsx 
// 마운트 시 버전 토큰 저장
const knownUpdatedAtRef = useRef(site.updatedAt);

// 4초 디바운스 자동 저장
const scheduleAutoSave = () => {
  clearTimeout(autoSaveTimerRef.current);
  setIsDirty(true);
  autoSaveTimerRef.current = setTimeout(async () => {
    const result = await saveSiteJsonAction(
      site.id,
      siteJsonRef.current,
      knownUpdatedAtRef.current,   // ← 토큰 동봉
    );
    if (result.error === 'STALE_VERSION') {
      setConflictDetected(true);    // ← 충돌 모달
    } else {
      knownUpdatedAtRef.current = result.updatedAt; // 토큰 회전
    }
  }, 4000);
};
포인트 · 토큰은 useRef에 저장 — 리렌더 없이 항상 최신값 유지.
② 서버 액션 — 토큰을 유즈케이스로 전달 actions.ts 
export async function saveSiteJsonAction(
  siteId: string,
  siteJson: TemplateJson,
  expectedUpdatedAt?: string,    // ← 클라가 보낸 토큰
) {
  return withUser(async (user, supabase) => {
    const useCase = createUpdateSiteJsonUseCase(supabase);
    const site = await useCase.execute(
      siteId, siteJson, user.id, expectedUpdatedAt,
    );
    return { success: true, updatedAt: site.updatedAt };
  });
}
포인트 · 도메인 에러(STALE_VERSION)는 withUser 헬퍼가 자동으로 { error: code }로 변환.
③ Postgres RPC — 락 + 비교 + 갱신을 한 트랜잭션에 010_optimistic_concurrency.sql 
CREATE OR REPLACE FUNCTION save_site_template_with_lock(
  p_site_id              UUID,
  p_new_json             JSONB,
  p_new_usages           JSONB,
  p_expected_updated_at  TIMESTAMPTZ DEFAULT NULL
)
RETURNS TEXT  -- 'OK' | 'STALE_VERSION'
AS $$
BEGIN
  -- ① 행을 잠근다 (다른 트랜잭션 못 끼어듬)
  SELECT updated_at INTO v_current
  FROM user_sites WHERE id = p_site_id
  FOR UPDATE;

  -- ② 토큰 비교 → 다르면 거부
  IF v_current IS DISTINCT FROM p_expected_updated_at THEN
    RETURN 'STALE_VERSION';
  END IF;

  -- ③ 같으면 JSON 갱신 + updated_at 자동 변경
  UPDATE user_sites
  SET site_json = p_new_json, updated_at = now()
  WHERE id = p_site_id;

  RETURN 'OK';
END;
$$;
포인트 · FOR UPDATE로 행을 잠그지 않으면 비교와 UPDATE 사이에 다른 트랜잭션이 끼어드는 TOCTOU race condition이 발생할 수 있음.
STEP 5 · 면접 한 줄 멘트

이렇게 말하면 끝

자동 저장으로 인해 다탭/다디바이스 환경에서 silent overwrite가 발생할 수 있다는 문제를 인지하고, 클라이언트가 자신이 본 버전의 updated_at을 토큰처럼 들고 다니다가 저장 시 함께 전송하게 했습니다. 서버는 Postgres RPC 안에서 FOR UPDATE 락으로 행을 잠그고 토큰과 현재 값을 비교해 다르면 STALE_VERSION을 반환합니다. 클라이언트는 이를 받아 Reload / Keep Editing 모달로 사용자에게 결정권을 넘기고, 보조 방어선으로 beforeunload 가드를 둬서 디바운스 윈도우 내 닫힘도 차단합니다.
STEP 6 · 꼬리 질문 대비

면접관이 파고들 만한 질문

클릭해서 펼쳐서 답변 미리 연습.

그런데 다중 로그인이 실제로 돼요?
네, Supabase Auth는 기본적으로 멀티 세션을 허용합니다. 다만 이 문제의 본질은 다중 디바이스가 아니라 "클라이언트 상태가 분리된 채로 같은 행을 갱신할 수 있는 모든 상황"입니다. 같은 브라우저의 두 탭만으로도 똑같이 발생하기 때문에, 인증 정책으로 푸는 게 아니라 데이터 레이어에서 버전 토큰으로 푸는 게 맞다고 판단했습니다.
왜 별도 version 칼럼이 아니라 updated_at을 썼나요?
updated_at은 이미 DB가 자동으로 찍어주는 값이라 추가 칼럼/마이그레이션 없이 재활용할 수 있었습니다. 정밀도는 timestamptz의 마이크로초 단위라 사람이 4초 디바운스로 부딪칠 확률은 사실상 0입니다.
FOR UPDATE 락이 꼭 필요한가요?
없으면 TOCTOU race condition이 발생할 수 있습니다. 비교(SELECT)와 갱신(UPDATE) 사이에 다른 트랜잭션이 끼어들면 두 클라이언트 모두 토큰 비교를 통과한 뒤 순차 UPDATE를 실행할 수 있거든요. FOR UPDATE로 행을 잠그면 한 트랜잭션이 끝날 때까지 다른 트랜잭션은 대기합니다.
STALE_VERSION을 예외가 아니라 문자열로 반환한 이유는?
PL/pgSQL의 RAISE EXCEPTION은 트랜잭션을 abort시켜 비용이 크고, Supabase 클라이언트에서 에러 코드 매핑이 번거롭습니다. 도메인 신호는 정상 반환값으로 처리하는 게 의미 전달도 명확하고 비용도 작습니다.
충돌을 자동으로 머지하지 왜 사용자한테 떠넘기죠?
사이트 JSON은 깊은 트리 구조(pages → sections → data → fields)라 의미 있는 자동 머지가 어렵습니다. 잘못된 머지는 데이터 손실보다 더 나쁜 결과(이상한 페이지)를 만들 수 있어서, 사용자에게 결정권을 주는 게 가장 안전한 선택이라고 판단했습니다.
자동 저장 4초는 왜 4초인가요?
타이핑 중 모든 키스트로크에 저장을 보내면 네트워크 비용이 너무 크고, 너무 길면 비정상 종료 시 손실 윈도우가 커집니다. 4초는 "키 입력 일시정지" 휴리스틱으로 잡은 절충값이고, 그 안에 닫혀도 beforeunload로 보조합니다.
팀 협업 단계로 확장하면 이대로 충분한가요?
아니요. 현재 모델은 "1인 다디바이스"에 최적화된 단계입니다. 실시간 협업으로 가려면 CRDT(Yjs/Automerge) 기반 실시간 머지가 필요하고, Postgres가 아닌 별도 상태 동기화 레이어(WebSocket + OT/CRDT)를 도입해야 합니다. 현재는 그 단계로 가기 전 "silent data loss만큼은 절대 없다"는 최소 보장 단계입니다.
