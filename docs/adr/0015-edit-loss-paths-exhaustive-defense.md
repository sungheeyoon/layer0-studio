# 편집 손실은 동시성 문제가 아니라 경로의 집합이다 — 전수 열거와 방어

> **Status: Accepted — 구현 완료.** 언마운트 flush + 전송 실패 한정 유한 재시도 (`src/lib/editor/flush-retry.ts`) · `visibilitychange(hidden)` flush (`src/lib/editor/use-flush-on-hidden.ts`) · `AUTOSAVE_MAX_WAIT_MS = 15_000` (`src/lib/editor/autosave-schedule.ts`) · 단일 write queue (`src/lib/editor/write-queue.ts`) · blocking→warning 강등 · `layout` 에디터 컨트롤 제거.

[ADR-0004](./0004-optimistic-concurrency-via-rpc.md) 는 편집 손실을 **동시성 문제**로 모델링하고 그 한 갈래(탭 간 silent overwrite)를 RPC 로 정확히 막았다. 그 결정은 지금도 옳다. 문제는 그것이 손실의 **유일한** 갈래인 것처럼 취급됐다는 점이다. 같은 데이터가 사라지는 경로는 그 뒤로도 열려 있었고, 각각 전혀 다른 메커니즘을 갖고 있었다.

이 ADR 은 손실 경로를 전수 열거하고, 각 경로에 대해 **어디까지 막고 어디부터 막지 않는지**를 명시한다. 부분적으로만 열거된 위협 모델이 이 결함의 원인이었으므로, 열거 자체가 결정의 일부다.

## 배경 — 실제로 열려 있던 경로

`DynamicEditor` 는 4초 idle 디바운스로 저장한다. 여기서 세 갈래가 나온다.

1. **이탈.** 언마운트 `useEffect` 는 타이머를 `clearTimeout` 할 뿐 flush 하지 않았고, `beforeunload` 핸들러는 `e.preventDefault()` 만 해서 경고창을 띄울 뿐 저장하지 않았다. 그리고 에디터 크롬에는 `<Link href="/dashboard">` 뒤로가기 버튼이 박혀 있다 — SPA 이동이라 `beforeunload` 는 아예 발화하지 않는다. **가장 자연스럽게 누르는 버튼이 곧 조용한 손실 경로였다.**

2. **디바운스 창에 상한이 없었다.** 매 키 입력이 타이머를 리셋하는데 `maxWait` 이 없어서, 4초 이상 손을 멈추지 않고 타이핑하면 저장은 **한 번도** 발화하지 않는다. 손실 창은 "최대 4초"가 아니라 원리상 무한이었다.

3. **검증 실패가 함정문이었다.** 이게 가장 심각했다. `globalStyles.layout` 은 **어떤 렌더러도 읽지 않는다** — 네 곳의 렌더 경로(`site/[domain]`, `preview/[id]`, `preview/preset`, 에디터) 중 어디도 CSS 변수로 주입하지 않고 `OVERLAY_MAP` 에도 없다. 그런데 `validateContent` 는 그 값을 **blocking** 으로 검증했고, 에디터 드롭다운이 제공하는 3개 중 2개(`centered`, `full-width`)가 `KNOWN_LAYOUTS` 에 없었다. 게다가 모든 프리셋은 `layout: 'wide'` 인데 `wide` 는 드롭다운에 없어서 컨트롤이 **빈 칸으로 보였다** — 유저가 채우려고 클릭하면 2/3 확률로 그 Site 의 **모든 저장이 영구 실패**했고, `wide` 로 되돌릴 UI 경로도 없었다.

그리고 셋과 별개로, 저장 경로들 사이에 **직렬화가 없었다.** `handleSave` 는 `clearTimeout` 으로 *타이머* 만 죽이고 이미 in-flight 인 자동저장은 못 막는다. `lastSaveRef` 의 2초 throttle 은 마지막 *성공* 시각을 보므로 응답 대기 중에는 통과한다. 결과: 자동저장이 나가는 순간 저장 버튼을 누르면 두 요청이 같은 `expectedUpdatedAt` 을 들고 경합해 **자기 자신과 STALE 충돌**하고, 혼자 한 탭에서 편집하던 유저에게 "다른 곳에서 수정되었습니다" 모달이 떴다. ADR-0004 는 **탭 간** 동시 쓰기를 막았지만 **탭 내** 동시 쓰기는 아무도 막지 않고 있었다.

## 결정

### 1. 불변식은 "서버 도달 보장" — 로컬 초안 저장소는 만들지 않는다

"에디터를 떠나는 모든 경로는 떠나기 전에 서버 저장을 완료한다"를 목표로 한다. 로컬(IndexedDB 등) 초안 + 복구 UI 는 택하지 않는다 — 열거된 손실 경로가 전부 "사용자가 의도적으로 떠나는" 경로라 서버 도달 보장으로 덮이고, 로컬 사본은 **"로컬과 서버 중 무엇이 최신인가"** 라는 ADR-0004 와 같은 종류의 문제를 하나 더 만들면서 정작 저 경로들을 더 확실히 막지도 못한다. 크래시 복구가 실제 불만으로 올라오면 그때 이 위에 얹는다.

### 2. flush 는 언마운트 cleanup 하나로, 탭 닫기는 범위 밖

언마운트 cleanup 에서 await 없이 저장을 발사한다. SPA 이동(뒤로가기 링크)과 브라우저 뒤로가기(popstate) 둘 다 페이지가 살아있으므로 요청이 끝까지 간다 — **경로 하나로 두 갈래가 덮인다.**

`<Link onNavigate>` 게이트(Next 16 지원)는 **쓰지 않는다.** 그것으로 살 수 있는 건 뒤로가기 *버튼* 에서의 실패 가시성뿐인데, 정작 같은 실패가 브라우저 뒤로가기에서는 여전히 조용하다. 일관되지 않은 부분해를 위해 `editor/layout.tsx` 를 Client Component 로 내리고 레이아웃 경계를 가로지르는 dirty-state Context 를 신설할 값어치가 없다.

**탭 닫기 / 새로고침은 범위 밖이다.** unload 중에는 Server Action 의 fetch 가 취소되고 `keepalive` 를 붙일 방법이 없다. `navigator.sendBeacon` + 전용 Route Handler 로 저장할 수는 있지만, 그건 ADR-0004 가 "우회하지 말라"고 못 박은 종류의 **새 저장 경로를 `withUser` 인증 레이어 밖에** 하나 더 만드는 일이다. 얻는 것은 "경고창을 보고도 나가기를 누른 사용자"의 마지막 몇 초다. 교환비가 맞지 않는다. 이 경로는 `beforeunload` 경고 + 아래 `maxWait` 으로 손실 창을 **상한 있는 값으로 고정**하는 것으로 갈음한다.

**`visibilitychange(hidden)` 에서도 flush 한다** (`src/lib/editor/use-flush-on-hidden.ts`). 처음 열거에서 빠졌던 이벤트인데, 위의 기각 근거가 **여기엔 적용되지 않는다** — `hidden` 은 페이지가 *살아 있는 채로* 발화하므로 보낸 요청이 완주하고, 따라서 인증 밖 새 경로가 필요 없다. 언마운트 flush 와 같은 "페이지가 살아남는 이탈" 범주다.

건지는 것은 주로 **모바일 홈 버튼**이다. 탭이 백그라운드로 가도 언마운트는 일어나지 않아 위의 cleanup 은 돌지 않고, 백그라운드 탭은 `setTimeout` 이 스로틀되므로 아래 `maxWait` 이 **상한 구실을 못 하는 바로 그 순간에** OS 가 탭을 회수할 수 있다.

가드는 언마운트 flush 와 같은 신호(살아 있는 디바운스 타이머)를 쓴다 — 탭 전환마다 저장하는 게 아니라 **집어가지 않은 편집이 있을 때만** 나가고, 첫 flush 가 타이머를 비우므로 전환을 반복해도 저장이 쌓이지 않는다. 언마운트 flush 와 달리 여기서는 컴포넌트가 **마운트된 상태**라 실패를 보고할 화면이 있다 — 그래서 `runAutoSave` 로 디스패치해서 배너와 Conflict 모달이 탭 복귀 시 그대로 뜬다.

**이것이 탭 닫기 기각을 뒤집지는 않는다.** 데스크톱에서 탭을 닫아도 `hidden` 은 발화하지만 직후 페이지가 죽어 in-flight 요청 완주가 보장되지 않는다. 확률을 올릴 뿐이므로 `beforeunload` 경고는 그대로 유지한다.

flush 실패 3종 중 `STALE_VERSION` 은 ADR-0004 상 **버리는 게 정답**이고(다른 탭의 쓰기를 덮으면 안 된다), 검증 실패는 아래 4번이 없애며, **남은 전송 실패만 재시도로 건질 수 있다.**

그 하나를 **유한 재시도로 건진다** (`src/lib/editor/flush-retry.ts`). 처음에는 이것도 fire-and-forget 으로 뒀지만 — 화면 없는 백그라운드 쓰기 루프는 ADR-0004 가 막으려던 "유저가 인지하지 못하는 저장 경로"와 같은 종류라는 이유였다 — 그 논거가 성립하려면 *루프* 여야 한다. 실제로 도입한 것은 SPA 이동이 끝나기 전에 소진되는 **상한 있는 2회 백오프**(400ms · 1600ms)이고, 재시도 대상은 **allow-list** 다:

| 실패 | 재시도 |
|---|---|
| 전송 실패 (`NETWORK_ERROR` — Server Action 호출 자체가 throw) | ✅ 콘텐츠도 토큰도 멀쩡하므로 다음 시도가 실제로 안착한다 |
| `STALE_VERSION` | ❌ 재시도가 성공하면 그게 곧 다른 탭 덮어쓰기다 (ADR-0004) |
| 검증 실패 | ❌ 결정적 거절 — 다음 시도도 동일하게 실패한다 |
| 그 외 (서버의 `UNKNOWN` 포함) | ❌ 분류되지 않은 코드는 재시도하지 않는 것이 기본값 |

전송 실패에 `UNKNOWN` 과 구분되는 코드를 준 것이 이 정책의 전제다. 서버가 **돌아서** 실패한 것(`UNKNOWN`)과 요청이 **닿지 못한** 것은 재시도 가치가 정반대인데, 예전에는 둘 다 `UNKNOWN` 이라 구분할 수단이 없었다. 재시도는 매번 큐에 다시 들어간다 — 그래야 3번의 순서 보장 안에 있고, 실행 시점의 최신 콘텐츠·토큰을 다시 읽는다.

재시도까지 실패하면 여전히 `console.error` 뿐이다. 이때 알릴 화면은 목적지 화면밖에 없고, 그 경로(`sessionStorage` 플래그 → 다음 화면 toast)는 채택하지 않았다.

### 3. 저장은 단일 큐를 통과한다

자동저장 · 초안 저장 · 게시 · flush 를 전부 하나의 promise chain 으로 직렬화한다. `lastSaveRef` 의 2초 throttle 은 제거한다 — 그건 위의 자기충돌을 어설프게 가리던 반창고였고, 큐가 있으면 의미를 잃는다.

flush 를 추가하는 것만으로 동시 쓰기 지점이 셋이 되므로 이 직렬화는 flush 의 **선행 조건**이다. ADR-0004 의 탭 간 방어에 대응하는 탭 내 방어이며, 둘이 합쳐져야 "한 Site 에 대한 쓰기는 항상 순서가 있다"가 성립한다.

### 4. Blocking rule 과 Warning rule — 저장을 막을 자격의 정의

**blocking = 저장하면 렌더러가 깨지거나 데이터 무결성이 무너지는 것. warning = 결과가 보기 싫을 뿐인 것.**

`validateContent` 의 blocking 규칙 20개를 "유저가 에디터 UI 로 도달 가능한가"로 분류하면 정확히 4개가 나오고, **그 4개가 전부 후자였다**:

| 규칙 | 도달 경로 | 저장했을 때의 실제 결과 |
|---|---|---|
| `INVALID_COLOR` | 색상 텍스트 입력을 비움 | 색 하나가 기본값 |
| `INVALID_COLOR_FIELD` | 섹션 color 자유 입력에 비-hex | 색 하나가 이상함 |
| `INVALID_FONT_SIZE` | 폰트 크기에 `16` (단위 없음) | 폰트 크기가 기본값 |
| `UNKNOWN_LAYOUT` | 레이아웃 드롭다운 | **아무 일도 안 일어남** |

나머지 16개(`UNKNOWN_COMPONENT_KEY`, `FIELD_TYPE_MISMATCH`, `DUPLICATE_SECTION_ID`, `MISSING_PAGE_SLUG` …)는 전부 프리셋 버그나 데이터 손상이지 사용자 입력이 아니다. 즉 **blocking 검증은 원래 개발자 버그 탐지기인데 사용자 저장 경로에 배치되어 있었고**, 유저가 실제로 트리거할 수 있는 규칙은 전부 손실을 감수할 만큼 심각하지 않았다.

`ContentModel` 은 통째로 검증되고 통째로 저장되므로, 한 필드의 오타가 **같은 Site 의 다른 모든 편집을 인질로 잡는다.** 색 하나가 이상하게 보이는 것과 편집 20개가 사라지는 것 중 후자가 명백히 나쁘다. 그래서 4개를 warning 으로 강등한다.

`layout` 은 검증 강등에 더해 **에디터 컨트롤 자체를 제거**한다. 소비처가 0인 필드를 유저에게 노출할 이유가 없다. 필드는 `GlobalStyles` 타입과 기존 데이터에 남는다(호환). 규칙을 blocking 으로 남긴 채 컨트롤만 지우는 선택지도 있었지만, 그러면 누군가 컨트롤을 되살리는 순간 같은 함정이 돌아온다 — 우리가 오늘 발견한 것이 정확히 그 종류의 실수다.

**ADR-0005 와의 관계:** 비-hex 값이 Design Token 메커니즘을 깨뜨린다는 관찰은 여전히 유효하다. 바뀐 것은 그 깨짐이 *조용하지* 않다는 점이다 — 아래 5번이 필드 옆에서 즉시 경고한다.

### 5. 클라이언트 검증은 차단이 아니라 즉시 피드백

`validateContent` 는 순수 함수이고 타입 외에 아무것도 import 하지 않으므로 클라이언트에서 **그대로 재사용**한다 (깊은 검증에 필요한 `templateLibrary` 를 에디터는 `templateModule.library` 로 이미 쥐고 있다). 규칙을 복제하지 않고 **서버와 클라이언트가 문자 그대로 같은 함수를 쓴다.**

역할은 **경고 표시 전용**이다. 무효값이라고 저장을 막지 않는다 — 막으면 손실 경로 #3 을 서버에서 클라이언트로 옮길 뿐이다.

서버의 `issues[].path` 는 클라이언트에 **노출하지 않는다** (`toActionError` 의 "코드만 반환" 계약 유지). 같은 함수로 미리 걸러내므로, 서버 검증 실패는 이제 "유저가 잘못 입력했다"가 아니라 **"클라이언트 게이트가 뚫렸다"는 개발자 신호** — 배포 스큐이거나 버그다. 셋 다 유저가 필드를 고쳐 해결할 수 있는 종류가 아니므로 짚어줄 값이 없다. `server-action.ts` 가 이미 `issues` 를 `console.warn` 으로 남긴다.

## 배포 순서 — 뒤집으면 이 수정이 새 손실을 만든다

**4번(검증 강등)이 `maxWait` 보다 먼저 배포되어야 한다.** 색상 자유 입력은 `#`, `#a`, `#ab` … 타이핑 중간 상태가 전부 무효인데, 지금은 4초 디바운스가 그 구간을 우연히 가려주고 있다. `maxWait` 은 그 가림막을 걷어낸다 — 천천히 타이핑하는 유저는 반드시 걸린다.

## 남겨둔 것

- **탭 닫기 / 크래시 시 최대 `maxWait` 분량 손실.** 2번에서 명시적으로 범위 밖으로 뒀다. 무한이던 창을 상한 있는 값으로 바꾼 것이 이번 이득이다. `visibilitychange` flush 가 이 중 **백그라운드 전환**(모바일 홈 버튼·앱 전환)은 걷어냈지만, 탭을 닫는 경우는 `hidden` 이후 페이지가 죽으므로 여전히 확률 문제로 남는다.
- **재시도를 다 쓴 flush 의 조용한 실패.** 전송 실패는 2번의 유한 재시도가 건지지만, 2회 모두 실패하면 유저는 이미 떠났으므로 알릴 화면이 없다. 손실 조건이 "네트워크가 순간 끊기면"에서 "약 2초 동안 계속 끊겨 있으면"으로 좁아진 것이지, 불변식의 완전 달성은 아니다.
