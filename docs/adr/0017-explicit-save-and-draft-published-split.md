# 저장은 사용자가 시키는 것이고, 게시는 복사다 — 자동저장 철회와 작업본/공개본 분리

> **Status: Accepted — 구현 완료.** 자동저장 인프라 4개 모듈 삭제 · `user_sites.published_content` + `asset_usages.scope` + `published_sites` 뷰 (migration 029) · `SECURITY DEFINER` 함수 전수 하드닝 (migration 028) · revision 기준 저장 표시 · 재진입 폐기 프롬프트 · 앱 내 이동 이탈 확인.
>
> **[ADR-0015](./0015-edit-loss-paths-exhaustive-defense.md) 를 대체한다(Supersedes).** 0015 의 위협 모델 열거는 여전히 읽을 값어치가 있지만, 그 결론(자동저장 + 이탈 flush + 재시도)은 이 문서가 뒤집는다.

## 왜 뒤집는가

ADR-0015 는 "편집을 잃지 않는다"를 목표로 잡고, 그 목표에서 역산해 방어를 쌓았다. 열거는 정확했고 구현도 열거를 충실히 따랐다. 뒤집는 이유는 열거가 틀려서가 아니라 **목표가 제품이 지려던 책임보다 컸기** 때문이다.

세 가지가 그 대가로 드러났다.

**첫째, 자동저장이 게시를 무의미하게 만들고 있었다.** 게시는 `user_sites.status` 를 `'active'` 로 뒤집는 일이었고, 공개 렌더러는 같은 행의 `content` 를 읽었다. 즉 **첫 게시 이후 모든 자동저장이 10초 뒤 공개 사이트에 나갔다.** "변경 사항 게시" 버튼은 첫 게시 이후 아무 일도 하지 않았고, 사용자가 문구를 지웠다 다시 쓰는 그 중간 상태가 방문자에게 보일 수 있었다. 손실 방지를 위해 만든 장치가 훨씬 큰 문제를 만들고 있었다.

**둘째, "✓ 저장됨"이 거짓말할 수 있었다.** 수동 저장/게시가 성공하면 응답 도중 들어온 편집과 무관하게 `isDirty=false` + `saved` 로 갔다. 자동저장 제품에서 이 표시는 사용자가 저장 버튼을 눌렀는지 기억하지 않아도 되게 만드는 **약속**이다. 약속이 부정확하면 나머지 방어가 다 정확해도 소용이 없다.

**셋째, 방어의 부피가 지키는 것보다 컸다.** `autosave-schedule` / `write-queue` / `use-flush-on-hidden` / `flush-retry` 네 모듈과 그 테스트 넷, 그리고 `DynamicEditor` 안의 상태 기계 전부가 **자동저장이 존재해서 생긴 파생 문제**를 막고 있었다. write queue 는 에디터가 자기 자신과 경합하는 것을 막는 장치인데, 그 경합은 자동저장이 사용자 클릭과 겹치기 때문에 생긴다. 원인을 없애면 파생 방어도 같이 사라진다.

## 결정

### 1. 저장은 사용자가 시킬 때만 일어난다

자동저장을 **제거한다.** `content` 는 사용자가 "임시 저장"을 누를 때만 바뀐다.

이것은 손실 위험을 줄이는 결정이 아니라 **책임 경계를 명시하는** 결정이다. 저장을 누르지 않은 편집은 제품이 지키겠다고 약속한 적 없는 상태이고, 그 상태를 몰래 서버에 올리는 것은 편의가 아니라 사용자 대신 결정을 내리는 일이다 — 특히 그 저장이 곧 공개로 이어지던 구조에서는.

보장선은 이렇게 읽는다.

| 상황 | 대응 | 보장 |
|---|---|---|
| 저장 버튼 → 성공 표시 | 서버 반영 | **보장한다.** 이후 조용히 사라지거나 덮어써지지 않는다 |
| 앱 내 이동(대시보드로 돌아가기) | 이탈 확인 모달 | **보장한다.** 앱이 통제할 수 있는 이동이므로 |
| 다른 탭·기기의 저장과 충돌 | `expectedUpdatedAt` + 충돌 모달 | **보장한다.** 기존 저장분을 덮어쓰지 않는다 |
| 탭 닫기 / 새로고침 | `beforeunload` 경고 | 보장하지 않는다 |
| 브라우저 뒤로가기 | 없음 | 보장하지 않는다 |
| 브라우저·OS 크래시, 배터리 방전 | 없음 | 보장하지 않는다 |

브라우저 뒤로가기가 유일하게 아쉬운 칸이다. `<Link onNavigate>` 로 앱의 뒤로가기 버튼은 막을 수 있지만(§4) `popstate` 에는 대응물이 없다. ADR-0015 는 이 칸을 언마운트 flush 로 덮었는데, 그 방법은 "사용자가 시키지 않은 저장"이라 §1 과 정면으로 충돌한다. 덮지 않는 쪽을 택한다.

**로컬 초안 저장소(IndexedDB)와 서버 버전 이력은 만들지 않는다.** ADR-0015 §1 의 기각 논리가 그대로 유효하고, 여기에 하나가 더 붙는다 — 자동저장이 없으면 "실수로 저장된 편집"이라는 것 자체가 없다. 저장은 명시적 행위이고, 되돌리는 수단은 §2 의 폐기와 편집 중의 Ctrl+Z 다.

### 2. 게시는 상태 플래그가 아니라 복사다

`user_sites` 에 두 벌을 둔다 (migration 029).

- `content` — 작업본. 저장으로만 바뀐다. 방문자에게 도달하지 않는다.
- `published_content` — 공개본. `publish_site_content` RPC 로만 바뀐다. `NULL` = 미게시.

이로써 저장과 게시가 각각 하나의 뜻을 갖는다. 저장은 "내 작업을 서버에 둔다", 게시는 "지금 작업본을 세상에 보인다".

파생으로 **폐기**가 성립한다. 작업본이 공개본과 다르면 되돌아갈 곳이 있다는 뜻이고, 에디터 재진입 시 "이어서 편집 / 폐기하고 되돌리기"를 물을 수 있다. 한 번도 게시되지 않은 Site 의 되돌림 기준은 생성 시 `snapshot`(템플릿 원본)이다.

폐기는 전용 RPC 를 만들지 않고 **통상의 콘텐츠 저장 경로를 탄다** (`SiteWriteUseCase.discardDraft`). 되돌린 내용도 검증돼야 하고 에셋 참조도 다시 계산돼야 하므로, 별도 경로를 파는 것은 ADR-0015 §1 이 금지한 "두 번째 저장 경로"를 만드는 일이다.

**`status` 의 뜻도 같이 좁아진다.** 예전에는 `active` 가 곧 게시였다 — 공개 렌더러가 draft 를 읽었으니 상태를 켜는 것이 콘텐츠를 공개하는 일이었다. 이제 무엇을 보여줄지는 `published_content` 가 정하고 `status` 는 **그것을 서빙할지 말지**만 정한다. 그래서 `AdminUpdateSiteUseCase.updateStatus` 는 moderation 도구로 다시 읽어야 한다.

| 전이 | 동작 |
|---|---|
| `→ active`, 공개본 있음 | 복구. 서빙 재개. `publishedAt` 은 건드리지 않는다 — 다시 올라가는 건 원래 올라갔던 그 콘텐츠다 |
| `→ active`, 공개본 없음 | **거절** (`NO_PUBLISHED_CONTENT`) |
| `→ suspended` / `draft` | takedown. 공개본은 남긴다 |

두 번째 칸이 결정이다. 그냥 켜지게 두면 관리자 화면에는 `active` 인데 공개 URL 은 404 인 상태가 만들어진다. 그렇다고 관리자가 남의 미완성 작업본을 대신 게시하게 하는 것은 이 역할이 의도적으로 가진 적 없는 **저작 권한**이고, 관리자와 게시 권한을 분리한 [ADR-0006](./0006-canpublishtemplates-separate-from-admin.md) 의 판단과도 어긋난다. 거절이 맞다.

### 3. 분리는 에셋 수명과 익명 읽기 경계를 함께 건드린다

JSON 컬럼만 둘로 나누면 두 군데가 조용히 깨진다. 마이그레이션 029 는 셋을 한 트랜잭션으로 묶는다.

**(a) 에셋.** `save_site_template_with_lock` 은 사이트의 `asset_usages` 를 통째로 지우고 다시 넣으면서 사라진 에셋을 `cleanup_queue` 로 보낸다(ADR-0003). 작업본에서 이미지를 지웠다는 이유로 큐에 넣으면 **그 이미지를 아직 쓰고 있는 공개 사이트가 깨진다.** `asset_usages.scope` (`draft` | `published`) 를 도입해 두 참조를 따로 세고, **양쪽에서 모두 사라졌을 때만** 회수 후보로 본다.

**(b) 익명 읽기.** RLS 는 행 단위라 "공개 사이트의 행은 읽되 작업본 컬럼은 못 읽게"를 정책으로 쓸 수 없다. 004 의 `read active published sites` 정책은 active 사이트의 행 **전체**를 누구에게나 내주므로, 분리를 해놓고 이 정책을 두면 PostgREST 로 `content` 를 직접 긁어 미게시 편집을 읽을 수 있다. 정책을 걷어내고 공개 컬럼만 담은 뷰 `published_sites` 로 익명 읽기 경로를 좁힌다. 도메인 모델에서도 공개 읽기는 `UserSite` 가 아니라 `PublishedSite` 를 반환한다 — 잘못된 사본을 서빙하는 것이 한 글자 실수가 되지 않도록.

### 4. 이탈 확인은 앱이 통제할 수 있는 이동에만

ADR-0015 §2 는 `<Link onNavigate>` 게이트를 "일관되지 않은 부분해"라며 기각했다. 그 판단은 **자동저장이 있다는 전제** 위에서 옳았다 — 저장이 알아서 되는데 확인창까지 띄우면 성가시기만 하다. 자동저장이 없어진 지금은 반대가 된다. 앱이 제공한 버튼을 눌렀는데 작업이 조용히 사라지는 것은 사용자가 이해할 수 없는 동작이고, 앱은 그것을 막을 수 있다.

레이아웃을 Client Component 로 내리지 않기 위해 dirty 상태는 Context 가 아니라 모듈 레벨 스토어(`src/lib/editor/unsaved-changes.ts`)로 공유한다. 에디터는 전체 화면 단일 라우트라 동시에 둘이 뜨지 않으므로 스코프 문제가 없고, 언마운트에서 플래그를 되돌린다.

### 5. "저장됨"은 편집 revision 기준으로만 뜬다

`revisionRef`(편집 카운터)와 `savedRevisionRef`(서버가 확인해준 revision)를 비교해, **둘이 같을 때만** 저장됨을 표시한다. 요청 중에 들어온 편집은 응답이 설명할 수 없는 편집이므로, 성공 응답이 와도 "저장되지 않은 변경 사항"으로 남는다.

카운터를 쓰는 이유는 콘텐츠 객체 비교가 틀려서가 아니라 같은 판정을 더 비싸게 하기 때문이다.

### 6. `SECURITY DEFINER` 함수는 호출 롤을 좁힌다

분리 작업 중 발견된 별개의 결함이라 같이 고친다 (migration 028). 이 저장소의 `SECURITY DEFINER` 함수 전부가 EXECUTE 권한을 회수한 적이 없었다 — PostgreSQL 은 신규 함수의 EXECUTE 를 기본적으로 PUBLIC 에 주고, Supabase 의 `anon`/`authenticated` 는 PUBLIC 을 상속한다. `SECURITY DEFINER` 는 RLS 를 우회하므로 "RLS 가 있으니 괜찮다"가 성립하지 않는다.

- `save_site_template_with_lock` — 함수 안에서 `auth.uid()` 로 소유권을 검사하고, `p_expected_updated_at` 의 DEFAULT 를 없애 토큰 없는 저장을 거절한다. EXECUTE 는 `authenticated` 만.
- `request_account_erasure` / `claim_cleanup_task` / `claim_asset_tombstones` / `sweep_orphaned_assets` — 전부 서비스 롤로만 호출된다. EXECUTE 를 `service_role` 로 좁힌다.
- 전 함수에 `SET search_path` 고정.

애플리케이션 레이어의 소유권 검사(`loadOwned` / `withUser`)는 RPC 를 직접 호출하는 자에게는 존재하지 않는다. 검사는 그 자체가 도달 가능한 경계에 있어야 한다.

## 결과

지워진 것: `autosave-schedule.ts`, `write-queue.ts`, `use-flush-on-hidden.ts`, `flush-retry.ts` 와 각각의 테스트, `DynamicEditor` 의 자동저장 상태 기계, i18n `editor.autosave` 키.

남은 것: `expectedUpdatedAt` + 충돌 모달(ADR-0004), `beforeunload` 경고, 경고를 blocking 으로 승격하지 않는다는 ADR-0015 §4 의 규칙(그대로 유효).

새로 생긴 것: 작업본/공개본 두 벌, `asset_usages.scope`, `published_sites` 뷰, `PublishedSite` / `EditorSite` 읽기 모델, 재진입 폐기 프롬프트, 이탈 확인.

## 남는 한계

명시해둔다. 이것들은 결함이 아니라 §1 이 그은 선의 반대편이다.

- 저장하지 않은 채 탭을 닫거나 브라우저가 죽으면 그 편집은 복구되지 않는다.
- 브라우저 뒤로가기는 확인 없이 떠난다.
- 이미 저장된 작업본으로 되돌아갈 수 있는 지점은 **마지막 게시본 하나**다. 그 이전 버전으로는 갈 수 없다.
- 029 백필의 기준선은 근사값이다. 029 이전 스키마에는 "마지막 공개본"이라는 값이 없었으므로, 한 번이라도 게시된 사이트(`published_at IS NOT NULL`)에 대해 마이그레이션 시점의 `content` 를 공개본으로 채택한다. 내렸다가 편집한 사이트는 그 편집분이 기준선에 섞인다 — 대안(템플릿 원본으로 되돌림)이 명백히 더 나쁘다.
- 충돌 모달은 방지 장치이지 병합 장치가 아니다. 충돌 후 선택지는 계속 편집(다음 저장도 다시 충돌한다)과 새로고침뿐이다.

마지막 항목은 실사용 불만이 올라오면 다시 볼 값어치가 있다. 나머지는 의도된 미보장이다.
