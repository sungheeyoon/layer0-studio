# 제안: 이상적인 템플릿 퍼블리싱 프로세스

_작성: 2026-06-27 — `outdoor-default`(능선) 제작 경험을 바탕으로._
_상태: **확정(Accepted)** — 2026-06-28 그릴링으로 6개 가지 확정, [ADR-0012](../adr/0012-template-publishing-pipeline.md)로 승격. 이 문서는 배경/논거이고, **확정안의 정본은 ADR-0012**다._

> **확정 요약(ADR-0012):** A안 채택 + 6개 결정 —
> ① 카탈로그 source = DB 행 유지(B안 기각). ② `status` 는 순수 DB 소유, **CREATE 기본값 `active`**(프리셋에 status 필드 안 둠), UPDATE 는 status 불변. ③ 등록은 **프로덕션 배포 성공 직후** Vercel 웹훅 → 보호된 엔드포인트가 `template:sync --apply`(머지 직후 아님 — 렌더러 미배포 크래시 방지). ④ CI = `tsc+eslint+verify --skip-capture` 차단 게이트, **schema-jsx array 거짓 양성 수정 선행**, 썸네일은 저작 시 커밋·CI 는 파일만 확인. ⑤ `canPublishTemplates` 를 등록 게이트 → **운영 공개/내림 토글** 게이트로 재배치(첫 공개는 머지가 게이트), 어드민 수동 sync 는 비상용으로 축소. ⑥ 가드: CREATE 썸네일 필수(못 구하면 등록 실패) + 롤백 2레인(archived 토글 / git revert+재배포) + version "diff 면 적용" 주석 정정 + takedown 내구성 회귀 테스트.
>
> 아래 §3 후보안·§4 이행경로는 **논의 당시의 초안**이며, 일부(예: "코드에 status 필드")는 그릴링에서 기각·수정됐다. 차이는 ADR-0012 §결정을 따른다.

> 출발 질문(사용자): "스킬로 좋은 사이트를 만들고 프리뷰로 확인까지 했는데, 굳이 어드민에서 `Apply Sync`를 눌러야 DB에 올라가는 게 맞을까?"

좋은 직관이다. 결론부터: **`Apply Sync`라는 수동 단계 자체는 본질이 아니다.** 진짜로 사람이 책임져야 하는 결정은 따로 있고, 지금 구조는 그 둘을 한 버튼에 섞어 놨다.

---

## 1. 지금은 어떻게 되어 있나

```
스킬로 저작 → 검증 게이트 → git 푸시 → 배포
   → 어드민 로그인 → [Sync from Code](미리보기) → [Apply Sync](DB 기록) → status를 active로 토글
```

DB에 `templates` 행이 생겨야 ① 카탈로그에 보이고 ② 사용자가 그걸 복사해 사이트를 만들 수 있다. 그 "행 만들기"가 `Apply Sync`다.

### 왜 이렇게 설계됐나 (정당한 이유들)
- **코드가 진실** (ADR-0002): templateJson/썸네일/버전은 항상 코드값으로 덮어쓴다. DB는 그 사본 + 운영 메타(이름/설명/상태).
- **프로덕션 DB 쓰기는 위험한 행위**: 그래서 `dry-run → apply` 2단계 + `canPublishTemplates` 권한 게이트 (ADR-0006).
- **상태 워크플로**: `draft / active / archived` — 코드에 없는 운영 개념.

즉 현행은 "실수로 프로덕션을 망치지 말자"는 **안전장치**로서 합리적이다. 문제는 그 안전장치가 **잘못된 지점**에 걸려 있다는 것.

---

## 2. 핵심 통찰: "등록"과 "공개"는 다른 행위다

지금 `Apply Sync` 한 버튼이 두 가지를 동시에 한다:

| 행위 | 성격 | 진짜 사람이 필요한가? |
|---|---|---|
| **등록(Register)** — 코드의 견본을 DB/런타임이 알게 함 | 기계적·결정적·되돌릴 수 있음 | ❌ 아니오. 이미 PR 리뷰 + CI 검증을 통과한 코드다 |
| **공개(Publish)** — 사용자에게 노출(`active`) | 외부로 나가는·의미 있는 결정 | ✅ 예. 이게 진짜 게이트여야 한다 |

**불편함의 정체**: 이미 (PR에서) 검증·리뷰가 끝난 코드를, 배포 후에 사람이 또 손으로 "등록" 버튼을 눌러야 한다. 등록은 사람의 판단이 1도 들어가지 않는 기계 작업인데 수동이다. 반대로 정작 의미 있는 "공개"는 `draft→active` 토글 한 번으로 가볍게 처리된다. **게이트가 거꾸로 걸려 있다.**

---

## 3. 이상적 모델 (후보 3안)

### A안 — 등록은 자동, 공개만 사람 ⭐ 추천
- **PR 리뷰가 곧 게이트.** 템플릿 PR이 머지되면 = 사람이 이미 승인한 것.
- 머지 → **CI가 `template:sync --apply --yes`를 자동 실행** (또는 배포 후 훅). 등록은 손 안 댄다.
- **공개 여부는 코드에 둔다**: preset에 `status: 'draft' | 'active'` 필드를 추가. PR에서 `active`로 두면 리뷰어가 "이건 바로 공개해도 됨"을 코드로 승인하는 셈. 긴급 내림(takedown)만 어드민 토글로.
- `canPublishTemplates`는 런타임 권한이 아니라 **"템플릿 PR을 머지할 수 있는 GitHub 권한"**으로 이동 → 게이트가 더 자연스러운 곳으로 감.

```
스킬 저작 → PR(검증 CI) → 리뷰/머지(=승인) → 자동 등록 → (코드 status=active면)즉시 공개
```

### B안 — 런타임이 코드를 직접 읽는다 (sync 제거)
- 카탈로그가 DB `templates` 대신 `presetMap`(코드)을 **직접 열거**. 코드 프리셋에 대해선 sync 파이프라인 자체가 사라짐.
- DB는 manual/시즌 한정 행 + 템플릿별 운영 메타(상태·노출순서)만 가벼운 테이블로 보관.
- 가장 급진적·가장 단순. 단, "코드 = 진실"을 끝까지 밀어붙이는 대신 런타임이 코드 번들에 더 결합됨(배포해야 반영).

### C안 — 현행 유지 + 마찰만 제거 (최소 변경)
- 2단계 버튼은 두되, **CI에서 미리 dry-run을 돌려 PR에 결과를 코멘트**로 남김(리뷰어가 미리 diff 확인).
- 어드민에서 `Sync from Code`를 생략하고 **"검증된 PR이면 Apply 한 번"**으로 축소.
- 가장 안전하지만, "왜 또 누르지?" 불편함은 남는다.

---

## 4. 추천과 이행 경로

**A안을 목표로, C안을 징검다리로.**

1. **(지금 당장)** `package.json`의 `template:sync`에 `--env-file=.env.local` 추가, `template:capture`의 OS 분기 수정 — 도구 마찰부터 제거 (`docs/template-authoring-friction.md` 참고).
2. **(짧게)** GitHub Actions에 템플릿 PR용 워크플로: `template:verify` + `template:sync`(dry-run) 결과를 **PR 코멘트**로. → 리뷰가 곧 검토가 됨.
3. **(본 게임)** preset에 `status` 필드 도입(코드가 진실). 머지 후 **CI가 `--apply`** 자동 실행. 어드민 `Apply Sync`는 **긴급 내림/올림 전용**으로 축소.
4. `canPublishTemplates`의 의미를 "런타임 권한 → 템플릿 PR 머지 권한"으로 재정의(또는 폐지하고 GitHub 권한으로 대체).

이렇게 하면 흐름이 이렇게 바뀐다:

```
[현행]  저작 → 푸시 → 배포 → 어드민 로그인 → Sync → Apply → active 토글   (사람 손 4번)
[A안]   저작 → PR(자동 검증) → 머지            → 자동 등록·공개            (사람 손 1번: 머지)
```

---

## 5. 트레이드오프 / 주의

- **자동 등록의 안전장치**: CI 검증(tsc/eslint/validate/verify)이 **반드시 차단 게이트**여야 함. 지금처럼 schema-jsx 거짓 양성으로 "사실상 안 막힘" 상태면 자동화의 신뢰 기반이 무너진다 → 그 검사부터 고쳐야 A안이 성립.
- **롤백**: 자동 등록은 되돌릴 수 있어야 한다(이전 버전 재배포 또는 status=archived). 등록이 "되돌릴 수 있음"이라는 전제가 깨지면 수동 게이트가 다시 정당해진다.
- **프로덕션 DB 직접 쓰기 우려**: CI가 service role 키로 prod에 쓰는 것을 경계해야 함 → 환경 분리(미리보기 배포는 staging DB)와 감사 로그(`template_sync_audit`) 유지.
- **"코드가 진실" 원칙은 지킨다**: A·B안 모두 사람이 DB JSON을 손으로 만드는 길을 늘리지 않는다 — 오히려 줄인다. ADR-0002와 충돌하지 않음.

---

## 한 줄 요약
> `Apply Sync`가 불편한 이유는 **사람 판단이 0인 "등록"을 수동으로 시키기 때문**이다. 사람이 책임질 건 "공개" 하나뿐. **PR 리뷰를 진짜 게이트로 삼고, 등록은 CI가 자동으로, 공개 여부는 코드(status)로** 옮기면 손이 네 번에서 한 번(머지)으로 준다. 단, 그 전제는 **CI 검증이 진짜로 막는 게이트**가 되는 것.
